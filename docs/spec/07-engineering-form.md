## 1. 技术栈

**维持原生 TypeScript + Sass，不引跨端框架。** 完整论证见 **ADR-0002**。此处只记对实现有约束力的后果：

1. **小程序没有 CSS 变量** —— 色调层只能落成 SCSS 变量（编译期）+ mixin（生成具体规则），device 的 `var(--x)` 做法不可照搬。这是 T2（#14）的技术核心。
2. **微信特有能力直接可用**：`wx.login`、`wx.scanCode`、`open-type="contact"`、`open-type="chooseAvatar"` —— 无编译层转译。
3. **不用 Vue 语法** —— 兄弟仓库 `smart-locker-admin` / `smart-locker-device` 的代码**不可移植到本端**（Web 运行时 ≠ 小程序运行时）。跨仓库只能借用**口径**（spec / ADR），不能借代码。

## 3. 目录结构

```
miniprogram/
├── app.ts / app.json / app.scss
├── api/            ← 端点函数（每个 13.x 一个模块）
├── types/          ← 手写 DTO（§7）
├── request/        ← 请求层（§4）—— 唯一发 HTTP 的地方
├── utils/          ← 纯函数（如 resolveLockerCode）
├── components/     ← 跨页组件（导航栏、空态、加载态、等待态……）
└── pages/          ← 页面，一个页面一个目录
```

**硬规则**：

1. **`pages/` 之外不得出现 `wx.request`** —— 一切 HTTP 走 `request/`。页面调 `api/` 的函数，不拼 URL、不拼 header。
2. **`api/` 不含业务分支** —— 它只做「入参 → 请求 → 出参 DTO」的搬运；状态判断、文案、跳转全在页面（或页面共享的组件）里。这样同一个端点在订单列表与详情页被用到时不会长出两套语义。
3. **`types/` 与 `api/` 一一对应** —— 一个端点模块配一个 DTO（§7）。

## 4. 请求层

请求层是**唯一的 HTTP 出口**，也是**登录失效处理的唯一场所**。形态：**Promise 封装 + 拦截器**（不用回调 + 手写队列 —— 排队重放与 Promise 链天然同构）。

### 4.1 职责边界（**请求层只归一化，不弹窗**）

请求层负责：附加 token → 发请求 → 判 HTTP 状态 + body `code` → **归一化成统一异常对象** → 交给调用方。

请求层**不负责**：弹 toast、弹 modal、决定跳哪儿、决定置灰谁。

**理由**：`01` §4 已定「全局失败出口**只有一个**，由启动态驱动，**不下放到各页面数据区**」；`04` §3 已定受限动作「**一律保持可见、可点、点击后解释**」。若请求层自作主张把每个 `code ≠ 0` 弹成 toast：

- 「点击后解释」会退化成**一堆互相覆盖的 toast**，用户来不及读，也看不到原因；
- `5004` 的**受限卡形态**（`04` §4，不是普通提示）会被提前弹掉，没机会出现；
- `06` §4.4 的 `6001` 组合（详情页没有参考金额 → 点了才报错）会被弹成 toast，而正确表现是**在动作点就地解释**。

**⇒ 页面拿到的永远是异常对象，由页面决定怎么讲。** 唯一例外是登录失效（§4.3），它确实是全局的。

### 4.2 业务错误形态（必须同时看两个地方）

⚠️ 契约是 **`HTTP 200 + code ≠ 0`** 承载业务错误（`API:1319`），只有认证/权限错用真 `401/403`（`API:44`）。**⇒ 请求层不得只看 HTTP 状态码，也不得只看 body `code`。**

统一异常对象至少含四个字段：

| 字段 | 说明 |
|---|---|
| `httpStatus` | HTTP 状态码（区分 401/403 与 200） |
| `code` | 业务码（`body.code`；非 JSON 响应或网络失败时为 `null`） |
| `message` | 服务端 `message` —— **按它展示，不硬编码文案**（`R1:435`） |
| `kind` | 归一化分类（见下表） |

归一化分类（`kind`）：

| `kind` | 触发 | 调用方预期行为 |
|---|---|---|
| `network` | 请求失败 / 超时 / 非 JSON 响应 | 按 `01` §4 或该动作自身的重试口径处理 |
| `unauthorized` | `401`（含 `2001` / `2005`） | **请求层内部消费**，不抛给页面（§4.3） |
| `forbidden` | `403` | 按受限处理 |
| `restricted` | `code === 5004` | **特判**：走 `04` §4 受限卡，**不展示服务端 message**（它既不解释原因也不给出路） |
| `business` | `200 + code ≠ 0`（其余） | **按 `message` 直出**，在动作点就地解释 |

**只有 `5004` 特判** —— 其余全部走服务端 `message`。这条与 `R1:435`「不硬编码文案」一致，且把特判面收到最小。

### 4.3 登录失效处理（单一飞行 + 全局排队重放）

承 `01` §3.4 状态机，请求层实现它：

```
带 access 发请求
├─ 2xx ──────────→ 正常返回
├─ 401 + 2001 ───→ 【入队】刷新一次（13.2，带 refresh）
│                    ├─ 成功 → 重放原请求
│                    └─ 失败 → 转「清态重登」
└─ 401 + 2005 ───→ 【入队】清登录态 → wx.login → 13.1 重登一次
                     ├─ 成功 → 重放原请求
                     └─ 失败 → 【全局失败出口】（01 §4），丢弃原动作
```

**硬约束**：

1. **单一飞行，全局一个队列。** 同一时刻只允许**一次**登录失效处理在飞；所有撞上 401 的请求进**同一个**队列，处理成功后统一按序重放。**不得按端点分别排队** —— `01` §3.3 的原文是「同一时刻只允许一次登录失效处理 —— 并发 401 不得触发多次刷新 / 重登」。冷启动时 5 个页面同时发请求是常态，没有这条就会打出刷新风暴。
2. **重放对写请求也安全。** `AppAuthInterceptor.preHandle` 在控制器**之前**抛异常（`AppAuthInterceptor.java:27-37`）⇒ 401 意味着请求**未被业务逻辑执行**，重放不构成重复提交（建单 / 取消 / 支付 / 建预约 / 转单同理）。**这是源码核实过的事实，不是推断。**
3. **重登也失败时绝不后台补发。** 丢弃原动作，进 `01` §4 全局失败出口。否则会出现「用户点了确认支付 → 网络断 → 用户离开 → 半小时后自动扣款」（`01` §3.3 硬口径 2）。
4. **真正「可能已生效但响应丢失」的是网络超时，不是 401** —— 那条分支靠**读接口核对状态**，**不靠重放**（`01` §3.3 硬口径 1）。
5. **`13.2` 与 `13.1` 自身不得触发这套逻辑**（否则递归）。它们是鉴权链的例外：`WebMvcConfig.java:46-47` 把 `/api/app/v1/auth/login` 与 `/api/app/v1/auth/refresh` 排除在 `AppAuthInterceptor` 之外 —— **只有这两个免鉴权**（与 `01` §1.1 一致）。请求层须硬编码这条豁免。

### 4.4 token 存储与过期判定

**裁决：access 与 refresh 都持久化到 `storage`；不在本地预判过期，完全靠 401 驱动。**

- **持久化**：`01` §3.2 附注把定稿权交给 D7，此处定案。access 2h / refresh 30d（`API:933,:941`）—— 若不持久化，两个有效期设置**在 C 端毫无意义**。微信 `storage` 无有效期限，与两者语义相合。
- **不预判**：不记 `expiresIn`、不比对本地时钟。**access 对不对由服务端说了算** —— 本地时钟偏移会导致误刷或漏刷，而 401 是权威信号且已有成熟处理链（§4.3）。少一份状态、少一处出错点。
- ⚠️ **已知副作用（有意接受）**：因为 `01` §5 **不做退出登录**（有意，非漏做），且 token 持久化 ⇒ **登录身份长期存在 `storage` 里，App 内没有任何清除入口**。用户唯一的「退出」方式是删除小程序或清微信存储。这是「登录无感 + 不做退出登录」两条裁决叠加的必然结果，**不是新引入的问题**。若将来加退出登录，清 `storage` 即可（`13.3 logout` 存在但一期不接）。
- **`13.6` 需要 access** ⇒ **未登录时连柜机信息都拿不到**（`01` §1.1）。冷启动扫码链路必须先完成登录再调 `13.6` —— 这不是特例，是 §4.3 链路的常规路径。

## 5. 页面与导航

**一期不分包。** 单包，全部页面进主包。

**理由**：主包上限 2MB，而本期页面共约 11 个，**全是原生 wxml/wxss + 全部数据走接口，没有任何本地图片或图标资源**（`project.config.json` 已设 `ignoreUploadUnusedFiles: true`）。空壳页面以几十 KB 计，离上限极远。分包唯一的收益是减小主包体积 —— 而主包**没有可减的大物**。⚠️ 顺带澄清一个常见误解：**分包并不能加快首屏**，它只减体积；首屏靠的是 `01` §3.2 的骨架屏。

**目录留出分包形状**（`pages/` 下按业务分目录），将来真需要分包时移动成本最小 —— 但现在**不改 `app.json`**。

**页面清单**（由 `01`–`06` 收敛，此处只记结构归属）：

| 层 | 页面 | 出处 |
|---|---|---|
| tabBar | 订单列表（默认首页，顶部常驻「扫码存件」）、我的 | `01` §2.3 |
| 主包非 tab | 柜机页、订单详情、**等待态**（`pages/waiting/` —— ✅ P1 #12 已定为**独立页**，三条入口以 **`redirectTo`** 进入，见 `08` §2） | `01` §6、`02` §8、P1 #12 |
| 主包非 tab | 预约列表、预约创建、信用分明细、计费说明 / 常见问题 / 联系客服 | `05` §6.1、`04` §7.3、`01` §5 |

**导航栏维持 `custom`（统一自绘）** —— `app.json` 现状即 `navigationStyle: "custom"`，**维持**。这不是偏好，是 `01` §2.4 的要求：柜机页是**冷启动、页面栈深度 1 的非 tab 页**（通道 A 扫码直达），系统返回 = 直接退回微信、底部 tabBar 不显示 ⇒ 屏幕上**没有任何通往订单列表的可见路径**，必须在页面顶部固定一个「我的订单」出口。**只有自绘导航栏能承载它。** 全端统一自绘，避免「有的页有自绘栏、有的页没有」的视觉与交互不一致。

## 6. 状态管理

**不引任何 store（不引 pinia、不引轻量库），用原生 `App.globalData` + 页面参数。**

**理由**：票面预设的三个「跨页状态」，经 spec 核对后**没有一个真的跨页**：

| 票面预设 | 实际裁决 | 出处 |
|---|---|---|
| 登录态 | **只在请求层内部**，不是 UI 状态（页面从不读它） | `01` §3.1 隐式前置登录、§3.4 状态机 |
| 柜机上下文 | **页面参数，禁入 storage、禁跨页共享** | `01` §6 + **ADR-0001** |
| 进行中订单 | **不缓存** —— 「看到就必须是真的」 | `01` §3.2 |

**⇒ 没有需要 store 承载的状态。** 引入 store 只会为「把业务数据缓存进全局」提供一个顺手的入口，而 spec 反复在对本地快照说不：`03` §2 / §6（列表 `onShow` 与下拉刷新**均重置回第一页**、**不轮询**）、`05` §8（预约列表同样重置）、`04` §5（**不做本地 `status` 快照** —— 本地快照会造出双源真相，还会把**已解禁用户挡在门外**）、`06` §3.4（「支付前」不是状态而是**派生**）。

**跨页传递只走两条路**：

1. **页面参数**（`navigateTo` 的 query）—— 如柜机页传 `code`、详情页传 `orderId`。
2. **`App.globalData`** —— 仅限**请求层自身**需要的少量值（token 句柄、单一飞行队列的状态）。**不放业务数据。**

## 7. 类型来源

**手写 DTO + 契约引用注释。不做 codegen。**

**理由**：

1. **契约的真源是 Markdown，不是机器可读产物。** 唯一事实源是 `java/smart-locker/docs/API设计文档.md` v1.0（96 端点三端一体）—— **不存在 OpenAPI / JSON Schema 产物**。所谓「脚本生成」意味着先写一个 Markdown 解析器，而**那个解析器就是第二份真源**，正是 `smart-locker-admin/docs/adr/0002` 花一整个 ADR 消灭的东西（双源漂移是结构性的）。
2. **一期只有 16 个端点。** 手写 DTO 的绝对成本很低，且换来一件 codegen 给不了的东西：**每条 DTO 字段旁边能写清那条陷阱**。
3. **R1 已捞出的 15 条字段陷阱是 Markdown 表格装不下的**，必须由类型层带住。典型：
   - **两个 `payAmount` 同名而语义不同** —— `13.11` 响应的 = **本次**支付额（`TIMEOUT` 补缴 = 差额）；订单字段的 = **累计实收**（`06` §1.5）。类型上必须是**两个不同的 DTO 字段**，注释必须写死。
   - **`openCommandIssued` 一期恒真**（`AppOrderServiceImpl.java:199` 写死 `true`）⇒ **不是「指令已下发」的证据**（`06` §1.4）。
   - **`estimatedAmount` 可空** —— 展示路径吞掉 `6001` 返回 `null`（`06` §1.9）⇒ 类型必须是 `number | null`，**不是 `number`**。
   - **`paid` / `openCommandIssued` 在 `13.11` 响应里都是布尔**，不可当凭据 —— 移交依据是 `code == 0`（`06` §7）。

**规则**：

1. **每个端点模块的 DTO 顶部带契约引用注释**：`// 契约：API设计文档.md §13.11 (:1057-1083)` —— 出处可回查，这是「不得自造契约」在代码层的落地方式。
2. **不发明字段、不改字段名、不合并语义不同的字段** —— 后端叫 `payAmount` 就叫 `payAmount`（哪怕它有两个）。
3. **可空字段必须显式标 `| null`** —— strict 模式下这是让 `06` §1.9 那类分支无法被忽略的机制。
4. **枚举值与后端逐字一致**（`IN_PROGRESS` / `TIMEOUT` / `MOCK_WECHAT`……）—— **中文映射属于 T1（#13）的文案表**，不进类型层。类型层是后端的形状，文案层是用户的语言，两者混在一起会让 T1 的表失去唯一事实源地位。
5. **找不到契约依据的字段不写** —— 宁可缺，不可编。发现契约缺口**登记到 map**，不改后端（Out of scope）。

## 8. 验收自查（本票的验收标准）

「新建一个页面时不需要再问『代码放哪、请求怎么发、类型从哪来』」—— 逐条对照：

| 问题 | 答案所在 |
|---|---|
| 代码放哪 | §3 目录结构（页面进 `pages/<name>/`，HTTP 进 `request/`，端点搬运进 `api/`，DTO 进 `types/`） |
| 请求怎么发 | §4 —— 调 `api/` 的函数，拿统一异常对象，**不自己弹窗** |
| 类型从哪来 | §7 —— 手写，按契约，带出处注释 |
| 登录失效怎么办 | §4.3 —— **不用管，请求层已处理**；只有重登也失败才进全局出口 |
| 要不要建 store | §6 —— **不建** |
| 要不要分包 | §5 —— **不分** |
| 导航栏怎么做 | §5 —— 自绘，统一 |
