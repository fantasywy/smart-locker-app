# 03 订单首页信息架构

> 承载 ticket：**D3（#7）**。契约源：`java/smart-locker/docs/API设计文档.md` v1.0 —— 用户端 **§13.7 / §13.8 / §13.9**、错误码 **§13.10**；需求 **§4.2 / §4.3 / §4.5**。事实源：`AppOrderServiceImpl.list()` / `BillingServiceImpl.estimatedAmount()` / `NotYetStoredDeadline`。
> 本文只写口径，不写实现代码。上游：`docs/spec/01-entry-and-identity.md`（§2.3 已定「首页 = 订单列表」）、`docs/spec/02-c-end-device-boundary.md`（§4 已定「列表行内不铺取件码」）。

## 1. 前提事实（实现者必须知道，否则下面的裁决看起来像任意选择）

1. **列表端点 `13.8` 只接受单个 `status` 值**，没有多值 / 分组 / 排序参数。多值语义（如「进行中」= `IN_PROGRESS|TIMEOUT`）**一次请求给不出来**。
2. **列表项没有 `createdAt`**（`AppOrderListItemVO`），字段只有：`id / orderNo / lockerId / lockerNo / siteName / cellNo / cellType / startAt / endAt / status / payAmount / estimatedAmount / pickupCode`。
3. **服务端排序是 `id DESC`**（`AppOrderServiceImpl.list()`，`id` 单调 ⇒ 等价于下单倒序）。客户端没有第二排序键可用：`startAt` 在未存入时为空，`createdAt` 根本不在响应里。
4. **`TIMEOUT` 是跨阶段状态**：`endAt == null` 是在途（待补缴 / 待取件），`endAt != null` 是已取件终局。⇒ **按 `status` 分组会把同一枚枚举劈成两半**，「进行中 / 已完成」两级模型与枚举本身错位。
5. **金额可见性底表**（`BillingServiceImpl.estimatedAmount` + `AppOrderServiceImpl.visiblePickupCode`）：

   | 情形 | `startAt` | `payAmount` | `estimatedAmount` | `pickupCode` |
   |---|---|---|---|---|
   | 未存入 | `null` | `null` | `null` | `null` |
   | 使用中 · 未付 | 非空 | `null` | **现算**（每 5 分钟向上量化） | 有 |
   | 使用中 · 已付待取 | 非空 | 定格实付 | **= `payAmount`**（已收敛，不再增长） | 有 |
   | `TIMEOUT` 在途 | 非空 | `null` 或**已付的一部分** | **现算，且继续累积** | 有 |
   | `COMPLETED` / `TIMEOUT` 已取 | 非空 | 定格实付 | `null` | `null` |
   | `CANCELLED` | `null` | `null` | `null` | `null` |
   | `FORCE_ENDED` | 非空 | 通常 `null`（强制结束只固化应收、不落实收） | `null` | `null` |

   ⇒ **`estimatedAmount` 是唯一会「边看边涨」的行**：它对 `TIMEOUT` 不收敛（代码注释原话：「TIMEOUT 的应收仍在累积，故只在 `IN_PROGRESS` 上收敛到定格值」）。契约亦明写它**禁止渲染为应付锁定价**。
6. **`openTimeoutMinutes` 只出现在 `13.7` 建单响应里**（`CreateOrderVO`），列表与详情都没有。
7. **未存入单的真实截止时刻是两段式**（`NotYetStoredDeadline.stageOf`）：第一程 = `createdAt + openTimeoutMinutes`；**开门指令未回执 `DONE` → 取消**；**已回执 → 延长一程**再看，仍无关门确认才标记「开门未闭」。其中「指令是否 `DONE`」（`openAcked`）**C 端完全看不到**。
8. **「开门未闭」在 C 端契约里没有字段**（`awaitingReview` 依赖管理端 `openedNotClosedAt`，用户端 §13.8 / §13.9 均不含）—— R3 findings 记录的**唯一真缺口**；后端改动在 Out of scope。
9. **分页越界钳制到末页**（`PageSupport`，缺省 `pageSize = 20`、上限 100）——「请求越界页返回空列表」**不会发生**。

## 2. 分组模型：单流，不分组

**首页是一个时间流，不做 tab、不做分段标题、不做筛选器。**

理由（全部来自 §1）：单值 `status` + 分页 + 无 `createdAt` 三条叠加，任何分组都在客户端自造一套与枚举错位的筛选语义 —— 「进行中」要两次请求合并，「已完成」跨 5 个枚举且劈不开 `TIMEOUT`；分段标题还会随翻页反复出现。

代价照实记：**老的在途单会沉到时间流底部**（例如 30 天前的 `TIMEOUT` 未取件），由 §3 的在途上浮补，且只补第一页。

顶部「扫码存件」常驻入口承 `01` §2.3，不受本节影响。

## 3. 排序与在途上浮

- **服务端顺序照用**：客户端不引入第二排序键（§1.2/§1.3）。
- **在途上浮只发生在第一页内**：渲染第一页前，把其中 `status ∈ {IN_PROGRESS, TIMEOUT}` 的项移到最前，组内保持服务端顺序；第 2 页及以后**不做任何重排**。
- **不加分隔标题**（加了就变成被打回的分组模型的弱化版），靠状态标签与色条区分。
- 上浮**不改变分页计算**：仍按服务端页号取数据，`total` 照用。

诚实边界：跨页不置顶（服务端不支持多值过滤，属 Out of scope）。若在途单不在第一页，它仍带有醒目的状态标签与语义色。

**首屏第一动机 = 「我东西还在里面」**（回访取件），因此首屏最前应当是最近的在途单 —— 这与服务端 `id DESC` 天然一致，在途上浮只是把「老在途单」也拉到同一位置。

## 4. 显示态清单（11 个枚举 → 9 个显示态）

派生只用 `status / startAt / endAt / payAmount` 四个字段，**不引入任何客户端侧的新数据**。

| # | 判定 | 显示态 | 性质 |
|---|---|---|---|
| 1 | `IN_PROGRESS ∧ startAt == null` | **待存入** | 在途 |
| 2 | `IN_PROGRESS ∧ startAt != null ∧ payAmount == null` | **使用中** | 在途 |
| 3 | `IN_PROGRESS ∧ startAt != null ∧ payAmount != null` | **待取件** | 在途 |
| 4 | `TIMEOUT ∧ endAt == null` | **已超时** | 在途 |
| 5 | `COMPLETED` ∨ (`TIMEOUT ∧ endAt != null`) | **已取件** | 终局 |
| 6 | `CANCELLED` | **已取消** | 终局 |
| 7 | `FORCE_ENDED` | **已结束** | 终局 |
| 8 | `REFUNDED` | **已退款** | 终局 |
| 9 | `PENDING_PAYMENT`（一期不启用） | 兜底：**原样显示枚举名，不做解释** | — |

- **⑤ 刻意合并**：`COMPLETED` 与「补缴取件后的 `TIMEOUT`」在用户视角是同一件事（东西拿走了）。
- **④ 刻意不二分「已补缴 / 未补缴」**：做不到 —— 见 §1.5，`TIMEOUT` 单的已付金额是过去某刻的定格，差额仍在累积。`estimatedAmount > payAmount` 的客户端派生**被否决**：该值是 5 分钟**向上**量化的参考快照，边界上会误报欠费。
- **⑥⑦⑧ 刻意不合并**：取消 / 人工结束 / 退款是三种不同的用户待遇。
- **每个枚举都有确定归宿，不存在「不知道该放哪」的状态。**

## 5. 行内版式

```
┌─┬────────────────────────────────────────────┬──────────┐
│▍│ 万达广场店                      WD-01 · M05 │ 使用中   │
│ │ 存入 04-01 09:00                           │          │
└─┴────────────────────────────────────────────┴──────────┘
```

| 位置 | 内容 | 口径 |
|---|---|---|
| 左缘 | 3px 语义色条 | 语义档见 §6；只在色条上用语义色原值 |
| 主行左 | 站点名 | 超长截断 |
| 主行右 | `柜机码 · 格口号`（`lockerNo` · `cellNo`） | 用户要去现场，位置是主信息 |
| 副行左 | 时间 | 在途 → `startAt`（存入时刻）；终局 → `endAt`；**未存入 → 留空**，改放固定引导「关好柜门才算存入」（§1.2 无 `createdAt` 可显示） |
| 副行右 | 状态标签 | 文案见 §6，终稿由 **T1 #13** 收口 |
| 整行 | 点击进详情 | **行内不放任何动作按钮**（取消在详情页，见 §7） |

- **行内不显示任何金额**。理由：列表是「找单」的地方；未付在途的金额随时间变（§1.5），显示它等于把参考值当锁定价；终局金额对用户的下一步行动没有影响。金额统一放详情页（那里有「参考」标注的语境）。
- **取件码不铺进行内**（承 `02` §4），只给进入详情的入口。

## 6. 状态 → 语义档 → 文案（三列映射草案）

硬规则承 device spec V25：**语义色只做色条 / 标签的背景与边框，标签文字一律走 ink**（琥珀 `#976a27`、红 `#c05454`、绿 `#008655`）。

| 显示态 | 语义档 | 文案草案（**终稿在 T1 #13**） | 依据 |
|---|---|---|---|
| 待存入 | **警示**（琥珀） | 待存入 | 需要你动作，且沉默到期会变「已取消」 |
| 使用中 | **正常**（品牌绿） | 使用中 | 在途、无需动作 |
| 待取件 | **正常**（品牌绿） | 待取件 | 在途、无需动作（门已开，等关门） |
| 已超时 | **危险**（红） | 已超时 | 欠费在累积，必须一眼可辨 |
| 已取件 | **中性**（灰） | 已取件 | 终局 |
| 已取消 | **中性**（灰） | 已取消 | 终局 |
| 已结束 | **中性**（灰） | 已结束 | 终局 |
| 已退款 | **中性**（灰） | 已退款 | 终局 |

五档里本列表只用四档（正常 / 警示 / 危险 / 中性）；具体 token 由 **T2 #14** 出。

## 7. 刷新与分页

| 事项 | 口径 |
|---|---|
| 首屏 | `pageSize = 20`（服务端缺省），`status` 不传（全部） |
| 加载更多 | 上拉触底取下一页；**终止条件只能是「已加载条数 ≥ `total`」** —— 越界会钳制到末页（§1.9），靠「返回空数组」判断会无限重复末页 |
| `onShow` | **静默刷新并重置回第一页**（丢弃已加载的后续页） |
| 下拉刷新 | 同 `onShow`，重置回第一页 |
| 常驻轮询 | **不做** |
| 取消（`13.10`） | **只在详情页**，且只在「待存入」时出现。取消有前置校验（开门指令已回执 `DONE` → `3002`，文案「柜门已开启，请放入物品后关门，或联系客服」），是需要解释的错误，行内放不下 |

- **重置而非增量刷新**：承 `01` §3.2「不做本地业务数据缓存 —— 看到就必须是真的」。在途单的状态会在翻页之间变，保留陈旧后续页等于让列表撒谎。订单量级小（个人用户），重置的代价低于陈旧数据的代价。
- **列表不轮询**：状态推进的关键时刻（关门结算）发生在用户站在柜机前，随后必然回到小程序，`onShow` 覆盖得到；常驻轮询耗电、被平台后台限制，而且**轮询到「门已开」也证明不了任何事**（`02` §8）。⚠️ **就地补正（2026-09-22，P1 #12）**：本句原写「真正的等待态轮询归 P1 的详情页」，**预设了等待态会轮询**。P1 的裁决是**等待态也不轮询** —— 等待期间 C 端手里的数据**恒等**（看不到指令状态、时间轴无「开门」事件），轮询买不到任何信息。见 `docs/spec/08-waiting-state.md` §3。**本节的「列表不轮询」结论不变、且更强。**

## 8. 异常浮现规则

**不做独立的「需要你处理」带。** C 端可见的「需要你处理」只有两类 —— **待存入**（待关门）与**已超时**（待补缴）—— 两者都是在途单，§3 的在途上浮已把它们送到最前；再做一条带等于同一单表达两次。

| 异常 | 列表里的表现 |
|---|---|
| **未存入** | 「待存入」标签 + 副行引导「关好柜门才算存入」；**不倒计时、不显示剩余时间**（见下） |
| **已超时** | 「已超时」标签 + 危险档色条。**不显示差额** —— 差额的准确值只在 `13.11` 支付时刻定格；`estimatedAmount` 是参考快照（§1.5），既不得渲染为锁定价，也不得用作客户端判欠费的依据 |
| **开门未闭** | **漏报**（保守方向）。C 端无字段（§1.8），`IN_PROGRESS ∧ startAt == null` 长期不动与「已延长一程」在 C 端**不可区分**，界面不做任何暗示。登记为联调挂账项，见 §10 |
| `CANCELLED` | **不额外解释** —— 状态自己说清；用户拿着的「我明明下了单」的困惑由「待存入」标签在其被取消前承担 |
| `FORCE_ENDED` / `REFUNDED` | 归终局中性档；用户侧不需要在列表里被惊动 |

**不倒计时的三个理由**（硬事实，不是偏好）：① `openTimeoutMinutes` 只在建单响应里（§1.6），冷启动后拿不到基准值；② 真实截止是两段式且依赖 C 端看不到的 `openAcked`（§1.7），任何倒计时都会在某些单上说谎；③ 补救手段（关柜门）不需要精确到分钟。

**倒计时唯一合法的位置**：~~**P1 #12** 的建单等待态 —— 那里有 `13.7` 刚返回的 `openTimeoutMinutes` 作实时基准，且订单是刚创建的。~~
⚠️ **就地补正（2026-09-22，P1 #12 收口）**：那个位置**确实存在**（建单路径有 `openTimeoutMinutes` 实时基准），但 **P1 裁决「有基准也不用」** —— 三条入口只有这一条有基准，做倒计时会让同一组件呈现两副面孔；且支付路径的订单可能建于几分钟前，倒计时会当场说谎。⇒ **本句收窄为：不倒计时**。见 `docs/spec/08-waiting-state.md` §8。**本节的「列表不倒计时」不变。**

## 9. 空态与首次进入

**一个空态，不区分「从没下过单」与「清空之后」。** 内容 = 一句说明 + 主行动「扫码存件」（复用顶部常驻入口）。

本模型没有筛选器，所以不存在「筛掉了所以空」的第二种空态；`01` §8 已定「首次进入 = 空订单列表」（`13.1` 首登自动注册对用户不可见）。

## 10. 登记项（跨仓库备忘，不改任何代码）

1. **物理门号 vs `cellNo` 不同源**：device 侧门面只显示**物理门号 `01`–`15`**（device spec V3），C 端只有 `cellNo`（如 `M05`），**映射表不在 C 端契约里**。不改 C 端也不改屏 —— **开哪个门由服务端 `OPEN_CELL` 指令决定，用户不需要凭编号找格口**，`cellNo` 只是行内的定位辅助信息。
2. **「开门未闭」的 C 端可见性缺口**（§1.8，承 R3）：唯一真缺口。本 effort **不提议改后端**；若将来补字段，它是订单列表的一个新增异常档，不影响本节的单流模型。

## 11. 刻意不做（避免被当成漏做）

- 不做 tab / 分段 / 筛选器（§2）。
- 不做跨页在途置顶（服务端不支持多值过滤）。
- 不做未存入的倒计时 / 剩余时间 / 紧迫度着色。
- 不在行内显示金额，不在行内放任何动作按钮（含取消）。
- 不在行内铺取件码。
- 不做列表轮询，不做本地业务数据缓存。
- 不用 `estimatedAmount > payAmount` 之类派生判欠费。
