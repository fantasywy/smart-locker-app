# 02 小程序 × 中控屏职责边界

> 承载 ticket：**D2（#6）**。契约源：`java/smart-locker/docs/API设计文档.md` v1.0 —— 用户端 **§13**、设备端 **§14.4 / §14.6**、错误码 **§15**、契约增量 **§16**；屏端事实源：`vue/smart-locker-device/src/device/{pickup,terminal}.ts` 与 R2 findings。
> 本文只写口径，不写实现代码。上游：`docs/spec/01-entry-and-identity.md`。

## 1. 前提事实（实现者必须知道，否则下面的裁决看起来像任意选择）

1. **开门只能由服务端下发的 `OPEN_CELL` 指令驱动**（`vue/smart-locker-device/docs/adr/0003`）。指令来源**只有三个**：

   | 触发 | 用途 | `reason` |
   |---|---|---|
   | `13.7 POST /orders` 创建存件订单 | 下单即开门（往里放东西） | `USER_DROP` |
   | `13.11 POST /orders/:id/pay` 支付订单 | **支付即开门**（把东西取出来） | `USER_PICKUP` |
   | 管理端手动开箱 | 人工 | `ADMIN_FORCE` |

2. **屏端 `pickup-verify` 不产生任何指令。** 它只回一次订单摘要 + `paid` + `hint`（`PickupVerifyServiceImpl.java:50-71`）。屏上那两句引导语是**后端写死的原文**：`paid:true` →「请在小程序点击取件开门」；`paid:false` →「请在小程序完成支付后取件」。
   ⇒ **屏上的取件码校验从不开门。**
3. 屏端唯一的取件输入是**键盘键入 6 位码**；屏端**没有入站扫码能力**（R2 §5）。「小程序出二维码给屏扫」需要给屏加扫码硬件与输入分支 —— 屏侧改造在 **Out of scope**。
4. 取件码的生命周期（R2 §3）：`DOOR_CLOSED` 存入关门后生成，6 位数字、**同一柜机内历史唯一不复用**；订单终局即失效（再次提交稳定返回 `CONSUMED`）。
5. **用户端 16 个端点里，没有任何一个能用取件码换开门**（R1 §0）—— `13.11` 只认 `orderId`，且只认**本人** token（越权 `8003`）。
6. `13.11` 的准入 = **已存入未取件**（`status ∈ {IN_PROGRESS, TIMEOUT}` ∧ `startAt ≠ null` ∧ `endAt == null`）；未存入 → `3002`（存件期的开门走 `13.7` 的 `USER_DROP`，C 端不调 `13.11`）；已取件 / 终局 → `3002`。
7. ⚠️ `13.11` 响应里的 `paid` 与 `openCommandIssued` 在**一期都是写死的 `true`**（`AppOrderServiceImpl.java:199`）⇒ `openCommandIssued` **不是**「指令真的下发了」的证据。
8. `estimatedAmount`（订单字段）与 `payable`（屏端字段）都是 **5 分钟粒度的参考快照**，契约明写**禁止渲染为应付锁定价**；真金额只在 `13.11` 的 `payAmount` 里定格回来。

## 2. 分工裁决

**屏 = 只读查询台；小程序 = 唯一开门发起方。**

| | 柜机中控屏 | 小程序 |
|---|---|---|
| 能做什么 | 收 6 位码 → 校验 → 显示状态与**参考**应付 → 引导用户回小程序 | 展示取件码、发起「取件开门」、支付 |
| 能开门吗 | **不能**（任何路径都不能） | 能，且只有它能 |
| 状态从哪来 | `pickup-verify` 响应 | 订单接口 `13.8` / `13.9` |

屏上引导语已由后端给出、与本节裁决一致，**屏侧无需改动**（见 §11）。

## 3. 取件码的定位：查询凭据，不是取件凭据

**取件码没有开门力。** 它唯一的作用是：用户站在柜机前，把它敲进屏上的键盘，让屏查出「哪一单、欠多少、付没付」，再把用户送回小程序完成开门。

这条必须写明，因为它与用户从**普通快递柜**带来的心智模型相反（那边是「输码即开门」）。任何界面措辞**不得**暗示「凭码取件」。

## 4. 展示口径

- **取件码只出现在订单详情页**的**固定取件区块**里，**常驻可见**。不做「点击才显示」，不做自动隐藏倒计时。
  理由：码无开门力 ⇒ 截屏 / 旁窥的损失只到「这人在这台柜机存过东西」；而它被用到的时刻永远是用户正对着柜机 —— 那也正是「取件开门」按钮所在的位置，一次进入就能同屏拿齐。
- **订单列表行内不铺 6 位数字**，只给进入详情的入口（列表结构归 D3 #7）。
- **不做防截屏、不做水印、不做自动隐藏。**
- 详情页取件区块里**预先讲清流程**（消解「输码即开门」的预期落差）：到柜机屏输入取件码 → 按屏上提示回到本页 → 点「取件开门」。屏上的 `hint` 只作**事后兜底** —— 它的发现时机是人已经站在柜机前，那是最糟的纠正时机。

## 5. 看不到取件码时怎么解释

`pickupCode` 仅在**已存入未取件**时非空（与 §1.6 同源）。两类空白，**只解释一类**：

| 情形 | 表现 |
|---|---|
| **未存入期**（已开箱、还没关门）—— 码**尚未生成** | 固定取件区块**占位 + 一句说明**：「关好柜门后才会生成取件码」。**不许留空白** |
| **终局后**（已取件 / 超时结算 / 取消 / 强制结束）—— 码**已失效** | **不解释、不出现取件区块**。终局订单提「取件码」只会让用户去找一个不存在的东西；状态（已取件 / 已取消）自己说清了 |

## 6. 「取件开门」动作

**一个按钮，按状态换文案与语义。** 它就是 C 端唯一的开门动作，实现 = **幂等调用 `13.11`**。

| 订单情形 | 按钮 | 语义 |
|---|---|---|
| 已存入、未付清 | **支付并开门** | 现算应付 → 支付成功 → 服务端下发 `OPEN_CELL(USER_PICKUP)` |
| 已存入、已付清（**仅 `IN_PROGRESS`**） | **取件开门** | 不重复扣费，**只重发指令**（前一条可能已 `FAILED`/`EXPIRED`） |
| 已存入、`TIMEOUT`（**无论已付多少**） | **补缴并开门** | 现算差额（累计应收 − 已付）；已付清则不再扣费，同样重发指令。⚠️ `TIMEOUT` 单**不存在**可以断言「已付清」的时刻，见 §7 |
| 未存入 / 已终局 | **无此按钮**（入口就不出现，见 §7） | 调 `13.11` 只会得到 `3002` |

三条硬口径：

1. **重试入口就是同一个按钮。** 指令 `FAILED`/`EXPIRED` 后不自动重发，必须由用户动作重新生成 —— 后端注释原话「此前那条指令可能已 FAILED/EXPIRED，用户重试动作必须重新生成」（`AppOrderServiceImpl.java:197`）。把它做成第二个入口，等于把重试变成隐藏路径。
2. **按钮不承载金额。** 客户端拿不到准确数字（§1.8）。金额单独一行展示并带「**参考**」二字；按钮只说动作。
3. **不拆「支付 / 开门」两个按钮**：用户端 16 个端点里只有 `13.11` 能落这件事，拆开是给用户一个假选择。

> 一期的**渠道形态**（纯模拟按钮 vs 套一层 `wx.requestPayment` 壳）是 **D6 #10**；点下去之后到 `DOOR_CLOSED` 之间那一段是 **P1 #12**。本节只定「动作存在、叫什么、何时可用、怎么重试」。

## 7. 两个派生判定

订单状态枚举里既没有「待取件」也没有「待支付」（`PENDING_PAYMENT` 一期不启用），C 端必须自己派生：

| 判定 | 口径 | 为什么 |
|---|---|---|
| **能不能取件**（取件区块与按钮的显示条件） | **`pickupCode !== null`** | 该字段的返回口径（`IN_PROGRESS\|TIMEOUT` ∧ `startAt≠null` ∧ `endAt==null`）与 `13.11` 准入、`14.6` 校验**同源**。用它当唯一闸门，「有码」与「能取件」永远不会打架，也不会出现「显示了码却点不动」 |
| **付没付清** | **`payAmount !== null` ∧ `status === IN_PROGRESS`**（⚠️ 不是 `> 0`） | **全免单（应付 0）也会落一张 0 元 `SUCCESS` 支付单**；用 `> 0` 判会把全免单用户永远卡在「待支付」。<br>⚠️ **限定（2026-09-21 由 D3 #7 补正）**：`payAmount !== null` **只在 `IN_PROGRESS` 上等于「已付清」**。已支付但未关门取走的单会被 5min 任务转 `TIMEOUT`，而 `TIMEOUT` 的应收**继续累积**（`BillingServiceImpl.estimatedAmount` 只在 `IN_PROGRESS` 上收敛到定格值），此时 `payAmount` 只是过去某刻的定格 ⇒ 断言「已付清」是错的，按钮必须走「补缴并开门」。客户端**不得**用 `estimatedAmount > payAmount` 反推欠费 —— 该值是 5 分钟**向上**量化的参考快照，边界上会误报 |

## 8. 点完「取件开门」之后说什么

手上的真相只有三条：`orderStatus` 仍是 `IN_PROGRESS`（或 `TIMEOUT`）、`paid: true`、以及一期恒真的 `openCommandIssued`。

- **只能说**：「已发出开门指令，请到柜机前取物，取出后关好柜门」+ 停在等待态。
- **不许**渲染「门已开」「取件成功」—— 指令可能 `FAILED`/`EXPIRED`，而一期 `openCommandIssued` 恒真、证明不了任何事。
- 唯一能证明门真的开了的证据是 **`DOOR_CLOSED` 驱动的状态推进**（订单转 `COMPLETED`、格口释放、码失效）。

⇒ 交给 **P1 #12** 的核心输入：~~等待态只能建立在轮询上~~，只能陈述「已发出指令」，不能陈述结果。

- ✅ **P1 #12 已收口（2026-09-22）**：**「只能建立在轮询上」这个前提被推翻** —— 经源码逐字段核实，C 端**看不到指令的任何状态**（全部 C 端 VO 无 `commandStatus`/`openAcked`），且时间轴**没有「开门」事件** ⇒ **等待期间数据恒等，轮询买不到任何信息** ⇒ P1 裁决**不轮询**，只做 `onShow` 核对 + 手动核对按钮。**「只能陈述『已发出指令』」这条不变，且被落成状态机不变量**。另：关门有两条规则、落点相反（存入关门 = 刚开始；取件关门 = 已结束）。见 `docs/spec/08-waiting-state.md` §1、§3、§4。

## 9. 与中控屏九态的语义对齐表

⚠️ **对齐是语义级的，不是数据的**：C 端**看不到**屏的显示态，两者只通过订单状态与 `paid` 间接对上。屏的「待机 / 输入中 / 校验中 / 无效 / 传输失败 / 业务拒绝」都是**屏侧局部态**，C 端既不知道、也不该假装知道。

| 屏端显示态 | 屏上行为 | C 端对应物 | C 端该做什么 |
|---|---|---|---|
| 待机 / 输入中 / 校验中 | 屏侧局部 | 无 | 不感知 |
| **已付清** | `hint`「请在小程序点击取件开门」 | 已存入、已付清、未取件 | 详情页给「取件开门」 |
| **待支付** | `hint`「请在小程序完成支付后取件」 | 已存入、未付清 | 详情页给「支付并开门」+ 参考金额 |
| 无效 `INVALID` | 清空输入 | 无（屏不知道是谁敲错了） | 不感知 |
| **已核销** `CONSUMED` | 清空输入 | 订单已终局 | 无入口，状态自己说清 |
| 传输失败 | 保留输入 | 无 | 不感知 |
| 业务拒绝 `9001 / 9002 / 9003` | 照实显示 `code` + `message` | 无 | 不感知 |

## 10. 取件不可达时的兜底

这套架构把取件绑在「**本人微信 + 有网 + 小程序可用**」上：手机没电、没网、微信被清、或者东西是别人帮存的 —— 用户在柜机前**完全取不出东西**；而「把码发给别人」也没用（码无开门力，§3）。

- 详情页取件区块与「我的」页静态出口都写明：**取不到件请联系客服**。
- 人工出口是**管理端手动开箱 `ADMIN_FORCE`**（现成能力，`API设计文档.md:390`）—— 它**不触发自动结算**，后续由管理端 `FORCE_END` / `REFUND` 闭合。
- 「联系客服」在这里第一次从摆设变成**功能性**出口：它是取件路径唯一的人工通路。这也是它必须出现在**详情页**、而不只是「我的」页的原因。

## 11. 移交说明（跨仓库 —— **不改任何代码**，只出请求）

裁决结论：**屏侧不需要改。** 屏上那两句引导语已与 §2 的分工一致，屏端没有任何阻塞取件路径的缺陷。两条**登记项**（备忘，不是请求）：

1. **术语同步项**：屏上 `hint` 是后端写死的字符串（`PickupVerifyServiceImpl.java:36`）。C 端按钮名与本 spec 统一为「**取件开门**」；若将来任一方改名，屏上文案**不会跟着变**，需人工同步。
2. **观感冲突（不改，仅登记）**：屏端键盘的提交按钮文案是「**开门**」（`TerminalKeypadTab.vue:111`），但按下只做校验、不开门。与 §1.2 叠加起来会让用户预期「按了就该开」。按 Out of scope **不改屏**；若将来要动，这是屏侧的一个独立议题。

## 12. 刻意不做（避免被当成漏做）

- 不做「分享取件码 / 代取」入口；任何界面不出现「凭码取件」的暗示。真代取需要后端新增授权模型（谁有权代谁开门），本 effort **不提议**。
- 不做防截屏、不做水印、不做自动隐藏倒计时。
- 不拆「支付」与「开门」两个按钮。
- 不让取件码出现在订单列表行内。
- 不让「取件开门」按钮承载具体金额。
- 不渲染「门已开 / 取件成功」—— 只陈述「已发出开门指令」。
