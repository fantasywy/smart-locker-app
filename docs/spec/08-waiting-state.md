## 1. 前提事实（实现者必须知道，否则下面的裁决看起来像任意选择）

1. ⚠️ **C 端看不到开门指令的任何状态。** 这条是本文的地基，由**逐字段核实**得出，不是推断：
   - C 端全部 VO —— `AppOrderVO`（`id / orderNo / status / baseFee / overtimeFee / discount / payAmount / startAt / endAt / estimatedAmount / pickupCode`）、`AppOrderListItemVO`（13 字段）、`AppOrderLockerVO`、`AppOrderPaymentVO`、`AppOrderDetailVO`（`order + locker + timeline + payments`）—— **没有任何 `commandStatus` / `openAcked` / 指令字段**。
   - `DeviceCommandVO` 是**设备端**的，且它自己也**没有状态字段**（只有 `id / type / cellNo / orderNo / reason / createdAt`）。
   - ⇒ **`PENDING → SENT → DONE/FAILED/EXPIRED` 这条生命周期对 C 端完全不可见。**
2. ⚠️ **时间轴里没有「开门」事件。** `OrderTimelineEvent` 只有 6 个值：`CREATED`(下单) / `OPENED`(存入) / `FINISHED`(结束) / `CANCELLED`(取消) / `FORCE_ENDED`(强制结束) / `REFUNDED`(退款)。⚠️ **`OPENED` 指的是「存入关门」（`OrderTimelineAssembler` 里取 `order.getStartAt()`），不是「开门」。**
   - ⇒ 从「点了按钮」到「关门落定」之间，**时间轴不新增任何事件**。
3. ⇒ **等待期间，C 端手里的数据恒等。** 把 1 + 2 合起来：轮询 `13.9` 在整个等待期间会反复返回**完全相同**的响应 —— `status` 不变（`OPEN_CELL` 不改订单状态）、`payAmount` 不变（已在 `13.11` 同步响应里定格）、`pickupCode` 不变、时间轴不新增。**唯一会变的是终局。** 见 §3。
4. ⚠️ **`DOOR_CLOSED` 是两条规则，且落点相反**（`DeviceEventServiceImpl.submit`）。这是本文最重要的业务事实，票面把两条路混成了一条：

   | 规则 | 匹配 | 落点 | 是终局吗 |
   |---|---|---|---|
   | **规则 1** `matchNotYetStoredOrder` | 本格口 `IN_PROGRESS` ∧ `startAt IS NULL` ∧ 未取件 | 落 `startAt` = 关门时刻、**生成取件码**；`status` **维持 `IN_PROGRESS`** | ❌ **不是终局 —— 这才刚刚开始计时** |
   | **规则 2** `settlePaidPickupOrder` | 本格口 `{IN_PROGRESS, TIMEOUT}` ∧ `startAt` 非空 ∧ `endAt` 为空 | 落 `endAt`；`IN_PROGRESS → COMPLETED`；`TIMEOUT` **只补录 `endAt`、维持 `TIMEOUT`** | ✅ 终局 |

   - ⚠️ **规则 2 还要求 `hasSuccessfulPayment(orderId) == true`**，否则**直接 return**（不结算、不报错、不留痕）。
   - 规则 1 优先；不匹配才尝试规则 2；都不中即**仅留痕**。
   - ⇒ **同一个「等待关门」组件，存入路径关门后是「刚开始」，取件路径关门后是「已结束」。** 见 §5。
5. ⚠️ **`13.11` 幂等只保「钱」，不保「门」。** `createOpenCommand` 是**无条件 `insert`** —— 没有任何「已有 `PENDING`/`SENT` 指令就跳过」的守卫（源码核实）。而 device ADR-0003 定「开门只能由 `OPEN_CELL` 驱动」、每条指令都是一次真实开门动作。
   - ⇒ **重复调用 `13.11` 不会重复扣费（幂等），但会真的再开一次门。** 这与 `06` §3.3「重复调用代价为零」**需要一处修正**：代价对**账**为零，对**物理世界**不是零。见 §6.4。
6. **`13.11` 的可达错误码只有四个**：`3002`（状态不允许）/ `8003`（非本人）/ `3001`（订单不存在）/ `6001`（费率未配置）。`5004` 由 `requireNotBlacklisted` 判在**更前面**（`AppOrderServiceImpl` 第 89 行，在业务逻辑之前）。
7. **`openTimeoutMinutes` 只在 `13.7` 建单响应里**（`CreateOrderVO`）。`13.11` / `13.15` 的响应都没有它 ⇒ **只有建单路径有倒计时基准**。
8. **转单（`13.15`）响应是 `{orderId, orderNo, cellNo}`**，同样**没有** `openTimeoutMinutes`，也没有 `13.11` 那样的支付信息。
9. **`06` §7 的五条硬约束**（本文直接继承，不重新裁决）：移交后不得再渲染支付界面；等待态只能说「已发出开门指令」；移交依据是 `code == 0`（**不是 `paid`** —— 一期 `paid` 与 `openCommandIssued` 都写死 `true`）；移交后 `orderStatus` 仍是 `IN_PROGRESS`/`TIMEOUT`；转单路径复用同一移交点。
10. **无推送通道**（`05` §5.2）：状态推进只能靠拉取。本文的「拉取」定义见 §3。

## 2. 裁决一：独立页，且用 `redirectTo` 进入

**「等待关门」是一个独立页**（`pages/waiting/`），三条入口一律以 **`redirectTo`** 进入。

**理由**（这是 `01` §9 一直挂着未答的那一问的答案）：

- **为什么是独立页而不是详情页内的状态**：这个等待态需要**独占屏幕**——它是用户**站在柜机前**时唯一该看的东西（大号的「已发出开门指令」+ 下一步动作）。把它做成详情页的一个分支，会让「取件码 / 参考金额 / 订单时间轴」与它争夺注意力，而这些信息在**这一刻**全都没用（用户人就在柜机前，不需要再读一遍进度）。
- ⚠️ **为什么必须 `redirectTo` 而不是 `navigateTo`**：`06` §7 硬约束 1 明写「移交后**不得再渲染支付界面**」。若用 `navigateTo`，用户按返回键就退回了那个「支付并开门」页面 —— **等于绕过硬约束**，而且那个页面此刻已经无用（钱已扣、指令已发），再点一次就是**又开一次门**（§1.5）。`redirectTo` 让「退回支付页」这个状态**物理上不存在**。
- **返回键落到哪**：`redirectTo` 替换掉来路页面 ⇒ 返回键回到**订单列表 / 预约列表**（来路的上一层），**不是**回到支付页或柜机页。

**三条入口**（全部 `redirectTo` 进同一页，**同一个组件**，承 `05` §4.2）：

| 入口 | 端点 | 移交依据 | 携带参数 | `openTimeoutMinutes` |
|---|---|---|---|---|
| **建单** | `13.7` | 建单成功 | `orderId` + `openTimeoutMinutes` | ✅ 有（**唯一**） |
| **转单** | `13.15` | 转单成功 | `orderId` | ❌ 无 |
| **支付** | `13.11` | **`code == 0`** | `orderId` | ❌ 无 |

⚠️ **不传「我来取件还是存件」这个参数**（见 §5：落点由**服务端回显的 `startAt`/`status`** 决定，不由入口决定 —— 入口只决定「进页时说什么」，不决定「关门后变什么」）。

## 3. 裁决二：等待期间不轮询，只做 `onShow` 核对

**等待态不做任何轮询。** 状态推进的两个来源只有：

1. **`onShow` 静默核对** —— 用户从柜机前走回手机，小程序必然经历 `onShow`。
2. **「我关好门了，核对一下」按钮** —— 兜住「他取完东西直接看手机、小程序没进过后台」这一类。

**理由（本节是本文最关键的一条，因为票面预设有轮询）**：

- ⚠️ **轮询买不到任何信息**（§1.1 + §1.2 + §1.3 的直接推论）。等待期间 `13.9` 的响应**恒等** —— 唯一的变量是终局。⇒ 每 3 秒发一次请求，会拿到 20 份**一模一样**的数据，然后其中某一刻变成终局。这不是「更好的实时感」，这是**用请求换零信息**。
- **`DOOR_CLOSED` 是个「用户物理上刚做完的动作」**，随后他**必然**回到手机 ⇒ `onShow` 在这个语境下的命中率接近必然。这与 `03` §6 给列表定的节奏**同源**：「状态推进的关键时刻（关门结算）发生在用户站在柜机前，随后必然回到小程序」—— 列表据此不轮询，**等待态没有理由比列表更焦虑**。
- **代价照实记**：`onShow` 有一个真实盲区 —— 用户**站着不动**、小程序**始终在前台**（取完东西、没锁屏、没切走）。此时 `onShow` **不触发**，页面会停在等待态不动。**兜底就是第 2 条的核对按钮**，它是这个盲区的唯一出路，因此它**不是可选项**。
- ⚠️ **顺带更正 `03` §6 与 `02` §8 的一处措辞**：那两处写「真正的等待态轮询归 P1 的详情页」，预设了轮询存在。本文的裁决是**不轮询** —— 请以本文为准（`03` §7 的「列表不轮询」结论**不变**，这里更正的是「等待态会轮询」这个预期）。

## 4. 裁决三：等待态只陈述「已发出开门指令」

承 `02` §8，本文把它落成**机械保证**（见 §10 的原型不变量）：

| 允许说 | 禁止说 |
|---|---|
| 「**已发出开门指令**」 | 「门已开」「柜门已打开」 |
| 「请到柜机前取出物品，取出后关好柜门」 | 「取件成功」 |
| 「如果柜门没有反应，可以再试一次」 | 「开门失败」（我们**不知道**失败没失败） |

⚠️ **`openCommandIssued` 不能作为说出口的依据** —— 一期写死 `true`（`06` §1.4）。等待态的措辞**不依赖任何字段**，它陈述的是**我们刚刚做过的那个动作**（调用了 `13.11`），而不是**服务端或柜机的结果**。

## 5. 裁决四：关门落定后去哪 —— 由**服务端回显**决定，不由入口决定

承 §1.4：关门有两条规则、落点相反。**判定依据只能是服务端回显的字段**，不能是「用户从哪个入口进来的」（`04` §11 硬规则）。

核对时读 `13.9` 的 `order` 块，判定顺序：

```
核对 13.9
├─ status === COMPLETED                      → 【取件完成】终局
├─ status ∈ {IN_PROGRESS, TIMEOUT} ∧ endAt == null
│    ├─ startAt != null  → 【仍在等待】什么都没变，继续等（不得据此说「门还没关」）
│    └─ startAt == null  → 【仍在等待】放入路径尚未关门
└─ CANCELLED / FORCE_ENDED / REFUNDED        → 【已终局】按终局状态展示
```

**关门落定后的两种落点**：

| 路径 | 服务端回显 | 界面落点 |
|---|---|---|
| **取件** | `status === COMPLETED` | 原地换终局态：「**已完成取件**」+ 「回到订单列表」 |
| **存入**（建单 / 转单） | `status === IN_PROGRESS` ∧ `startAt != null` | 原地换终局态：「**已存入**」+ **取件码** + 「知道了」（回订单列表） |

⚠️ **存入落点必须显式处理，票面漏了它**：关门后订单**远未结束**（状态仍是 `IN_PROGRESS`，只是有了 `startAt` 与取件码）。这是 `02` §5 说的「关好柜门后才会生成取件码」那一刻，所以**取件码要在这里亮出来**。

⚠️ **但存入落点不得铺「取件开门」按钮** —— 那是**下次来取**时的事。此刻铺出来会误导用户以为「现在还要再点一下」，而他正站在柜机前、东西刚放好、下一步该走人。

⚠️ **组件不含落点逻辑**（本文与 `05` §4.2 的「复用同一组件」不冲突，而是它更干净的实现）：组件职责收在「陈述已发出指令 + 等关门发生」+ **向调用方回传「拿到新事实了」**；**去哪里由调用方决定**。三条入口的落点差异是**业务差异**（存入 vs 取件），把它塞进组件会让组件必须知道「我是从哪条路来的」——那是把调用方语义泄漏进组件。

## 6. 中断与异常：等待态没有「失败」可显示

### 6.1 三类中断，C 端全部不可观测

⚠️ **重写票面前提**：票面问题 2 问「`FAILED` / `EXPIRED` /『开门了但没关』三类中断各对应什么界面与措辞」。**这三类都不是 C 端能看见的状态**（§1.1）——

| 中断 | 真实发生位置 | C 端可见吗 | 界面表现 |
|---|---|---|---|
| 指令 `FAILED` | 服务端 | ❌ 不可见 | **与正常等待完全一致** |
| 指令 `EXPIRED`（`SENT` 超 5min） | 服务端定时任务 | ❌ 不可见 | **与正常等待完全一致** |
| 开门了但没关 / 上报丢失 | 柜机 | ❌ 不可见 | **与正常等待完全一致**，直到软超时（§6.3） |

⇒ **矩阵里不设这三行**（设了就是三个永远不触发的界面）。这与 `06` §4.1 对「支付失败」的处理**同构** —— 票面问了一个一期不可观测的分支，答案不是编界面，而是**重新表述这个等待态能说什么**。

### 6.2 用户唯一的出路：重试

**等待态常驻一个次级入口：「门没有反应？重试」**（存入路径文案：「门没有反应？重新开门」）。

- **重试 = 再调一次 `13.11`**（承 `02` §6.1「重试入口就是同一个按钮」+ `06` §1.7 幂等）。
- ⚠️ **措辞不伪装成失败**：只说「**如果柜门没有反应**」—— 这是个**条件句**，它诚实地表达「我们不知道」，而不是替服务端宣布「失败了」。**不许**写「开门失败，请重试」（那是替服务端宣布一个我们看不见的事实）。
- ⚠️ **不递增、不展示任何「重试次数」** —— 递增就等于我们在假装知道失败了。
- ⚠️ **不设自动重试**：自动重发会在用户没要求时**再开一次门**（§1.5）。

### 6.3 软超时：只换措辞，不跳走

设一个**纯客户端**软超时（不依赖任何请求，也不依赖任何服务端字段）。超时后：

- ✅ 追加一句：「**如果柜门已经关好，这里不会立刻变化；可以稍后在订单里查看。**」
- ✅ 等待按钮进入「等待中…」（不再暗示马上会有结果）。
- ❌ **不自动跳转、不自动退回、不停掉核对按钮。**
- ❌ **不换成「失败」措辞。**

**理由**：软超时若自动跳走，是**替用户做决定** —— 而此刻他可能正手忙脚乱地把东西塞进柜子，**把他从页面上赶走是主动伤害**。换措辞则只做一件事：**降低焦虑**，让页面不再暗示「一个很快会来的信号」。

⚠️ **为什么需要软超时**：`settlePaidPickupOrder` 要求关门事件到达（§1.4），而用户**忘记关门**或**柜机上报丢失**时，订单**永不结算**、`endAt` 永远为空，而 C 端**看不到任何异常**（`openedNotClosed` 不在 C 端契约，R3 登记）。⇒ **这个等待态没有一个「放弃」的自然时刻，必须由软超时兜住。**

⚠️ **软超时时长的最终取值归 T1**（本文只定「有这么一个时刻」）。

### 6.4 `13.11` 报错时（重试路径上撞到错误码）

重试可能撞上 `3002` / `6001` 等。按 `07` §4.2，`5004` 走受限卡、其余**按 `message` 直出、在动作点就地解释**（承 `04` §3「一律事后解释、绝不事前阻断」）。

⚠️ **`3002` 在等待态有特殊含义**：它表示订单**已经不在可取状态**了（多半是**已经取完了**）。⇒ 撞到 `3002` 时，**顺带触发一次核对**（§5）—— 用户看到的结果应是「已取件」，而不是一个孤立的报错。

⚠️ **`6001`（费率未配置）** 承 `06` §4.4：这是运营事故，出路只有客服；且它是**上线前置项**。

## 7. 防连点与重试的关系（对 `06` §3.3 的一处修正）

**裁决：防连点只保护「同一次请求在飞」，绝不阻止用户重试。**

- ✅ 请求进行中禁用按钮（技术性防抖）。
- ❌ **禁止**「本地判断这单已付过 → 不发请求」（承 `06` §3.3，理由不变）。
- ⚠️ **修正 `06` §3.3 的表述**：那一节说「重复调用 `13.11` 的代价是**零**」。这句话对**钱**成立（幂等），对**物理世界不成立** —— `createOpenCommand` **无条件插入新指令**（§1.5），每条指令都是一次真实开门。⇒ 准确的表述是：**「重复调用的账务代价为零，物理代价是再开一次门；这个交换仍然值得做，因为它是指令 `FAILED`/`EXPIRED` 之后唯一的重试路径。」**
- ⇒ **防抖窗口要覆盖「指令已发出的那一整段」**：等待态默认**不显示**可连点的重试按钮；重试入口的**呈现时机**由软超时或用户主动核对后决定。具体交互细节归 T1 / T2。

⚠️ **这条修正不改变 `06` §3.3 的结论**（仍然要做重试、仍然不做本地业务防呆），只把它的**理由讲准**。

## 8. 倒计时：不做（收窄 `03` §8 / `04` §11 的「唯一合法位置」）

**裁决：三条入口一律不做倒计时。**

- 只有建单路径有 `openTimeoutMinutes` 基准（§1.7），转单与支付路径**拿不到** ⇒ 同一组件会呈现**两副面孔**。
- 支付路径更糟：订单可能是**几分钟前建的**（用户先下单、放东西、过一阵才来取件），`createdAt + openTimeoutMinutes` **早已过期** ⇒ 倒计时会**当场变成负数或直接说谎**。
- `03` §8 已论证倒计时「必然在某些单上说谎」（真实截止是两段式 + 依赖 C 端看不见的 `openAcked`）。

⇒ ⚠️ **这等于主动收窄 `03` §8 与 `04` §11 交出的那条「唯一合法位置」**：本文裁决「那个位置**确实存在**（建单路径有实时基准），但我们**选择不用** —— 收益（催促用户快关门）远小于风险（说谎 / 三条路径两副面孔）」。**`03` §8「列表不倒计时」的结论不变**，且现在**更强**了：等待态也不倒计时。

## 9. 刻意不做（避免被当成漏做）

- **不做轮询**（§3）—— 等待期间数据恒等，轮询买不到信息。
- **不做自动重试 / 自动补发**（§6.2）。
- **不做指令 `FAILED` / `EXPIRED` / 「开门未闭」的失败界面**（§6.1 —— C 端不可观测，做了就是编）。
- **不做倒计时**（§8）。
- **不做「门已开 / 取件成功」的渲染**（§4）。
- **不自动跳转**（§6.3）。
- **不在存入落点铺「取件开门」按钮**（§5）。
- **不做等待态的本地缓存 / 本地状态快照** —— 承 `01` §3.2、`07` §6；等待态**不引 store**。
- **不给等待态加「进度百分比 / 进度条」** —— 没有任何服务端进度可依。

## 10. 与中控屏九态的语义对齐（承 `02` §9）

⚠️ **对齐是语义级的，不是数据的**：C 端**看不到**屏的显示态。九态里**没有一个**对应当前的「等待关门」—— 它们全是**屏侧局部态**。

| 现象 | C 端该做什么 |
|---|---|
| 屏上「待机 / 输入中 / 校验中 / 无效」 | **不感知**（用户在屏上敲码与 C 端无关） |
| 屏上「已付清 / 待支付」 | 不感知 —— C 端此刻**正在开门**，用户已经过了屏这个环节 |
| 屏上「**传输失败**」 | ⚠️ **不感知，且不等于 C 端的「开门失败」**。它是**屏 → 后端**的传输问题，与**服务端 → 柜机**的 `OPEN_CELL` 是两段不同的链路。**不得把屏的「传输失败」映射成 C 端的失败文案。** |
| 屏上「**业务拒绝**」 | ⚠️ **同上，不感知**。它是屏端 `pickup-verify` 的 `9001/9002/9003`，与 C 端 `13.11` 的错误码**不是一套**（承 `04` 的「单笔校验被拒」术语）。 |
| 屏上「已核销 `CONSUMED`」 | 订单已终局 ⇒ 核对时按 §5 落终局态 |

**结论**：中控屏九态**对等待态没有映射物**。票面要求「尤其传输失败与业务拒绝对应 C 端什么」—— 答案是：**都不对应**，它们与 C 端取件链路无因果关系。这条对齐表的价值在于**防止实现者去屏端找信号**。

## 11. 验收：原型验证过的不变量

原型（§12）把本文的裁决落成可执行的状态模块，并验证了 12 条断言（`verify.js`），其中最关键的三条**不变量**：

1. **核对接不到新事实时，状态必须不变** —— 不得用「数据没变化」推断「门还没关」（那是用不可见事实做断言）。
2. **指令 `FAILED`/`EXPIRED` 事件到达时，界面状态必须完全不变** —— 这是「C 端不可观测」的机械保证，也是 §6.1 的验收方式。
3. **任何可达状态下，都不存在一个能证明「门已开」的字段** —— §4 硬规则的机械保证。

## 12. 原型（throwaway）

- 文件：`.scratch/p1-waiting-prototype/waiting-state.html`（单文件，双击即开），行为验证：`verify.js`。
- **定位**：回答问题的一次性材料，**不是实现基础**。纯状态模块（`ENTRY` / `PHASE` / `initialState` / `reduce`）是唯一值得搬运的部分 —— 可原样搬进 `miniprogram/components/waiting/`；页面壳与 scenario 是 throwaway。
