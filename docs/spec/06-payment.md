## 1. 前提事实（实现者必须知道，否则下面的裁决看起来像任意选择）

1. **一期渠道只有 `MOCK_WECHAT`**，且**同步成功** —— `PaymentServiceImpl.CHANNEL = PaymentChannel.MOCK_WECHAT`，契约 `API:1071` 明写「一期模拟渠道**同步成功，不模拟失败分支**」。
   - ⚠️ **一期不存在「支付失败」这个事件。** `AppOrderServiceImpl.pay()` 没有任何失败返回路径：调用即扣费、即发指令、即返回成功。
   - ⇒ 票面问题 4 的「支付失败怎么表现」在一期是**空集**，§4 据此重写这一行（改为网络不确定性）。
2. **一期不套 `wx.requestPayment` 的壳在物理上也不可能**：`13.11` 是**同步完成**的（调用返回时钱已扣、指令已发），**没有任何预支付单**可供拉起 ⇒ 假 `prepay_id` 会让收银台里的「取消支付」变成谎话（用户取消了，钱其实已扣、门其实已开）。见 §2 裁决。
3. **`13.11` 是唯一能落「取件付费 + 开门」的端点**（`02` §1）。请求体 `{}`，**金额服务端现算，不信任前端传参**（`API:1057`）。C 端 16 个端点里**没有第二个**能付款或开门的。
4. **响应 `AppPayVO` 七个字段**（`AppPayVO.java:20-27`）：`payNo / payAmount / channel / paidAt / orderStatus / paid / openCommandIssued`。
   - ⚠️ **`openCommandIssued` 一期恒真**（`AppOrderServiceImpl.java:199` 写死 `true`）⇒ **它不是「指令真的下发了」的证据**（承 `02` §1.7）。
5. ⚠️ **两个 `payAmount` 同名而语义不同**（本文实测确认，**现有 spec 未曾记录**）：
   | 位置 | 语义 | 来源 |
   |---|---|---|
   | **`13.11` 响应** `payAmount` | **本次**支付金额（正常单 = 应付全额；`TIMEOUT` 补缴 = **差额**） | `AppPayVO` javadoc :12 |
   | **订单字段** `payAmount`（`13.8` / `13.9`） | **累计实收**（所有 `INCOME` 流水之和） | `PaymentServiceImpl.paidAmount` :97-104 |
   - **实测证据**（`AppTimeoutSettlementFlowTest` :103-141）：首付 20 → 响应 `20`；停用优惠后补缴，响应 `40`（差额），**同一订单字段变 `60`**。
   - ⇒ §6.2 必须写死详情页用哪一个。
6. ⚠️ **`orderStatus` 返回的是当前实际状态**（`IN_PROGRESS` / `TIMEOUT`），**不是** `COMPLETED`（契约增量 #8，`API:1076`）—— **支付成功 ≠ 订单完成**，结算由关门事件驱动。
7. **`13.11` 幂等**（`API:1068`，测试 `pay_repeated_doesNotDoubleCharge_butReissuesPickupCommand`）：已支付未取件重调 → **不重复扣费**、**重发 `OPEN_CELL(USER_PICKUP)`**、返回**首次**支付信息。
   - ⚠️ 「重发指令」是**有益副作用**：它**就是**指令 `FAILED`/`EXPIRED` 之后的唯一重试机制（承 `02` §6.1）。
8. **`13.11` 可达错误码只有四个**（`API:1067,:1082`，测试实证）：`3002`（状态不允许：未存入 / 已取件 / 已终局）、`8003`（非本人）、`3001`（订单不存在）、`6001`（费率未配置）。
9. ⚠️ **展示路径吞掉 `6001`，收费路径照常报**（`AppOrderServiceImpl.estimatedAmountForDisplay` :215-218 + `API:1025`）：费率未配置时 `13.8`/`13.9` 的 `estimatedAmount` 返回 **`null`**（不让一个展示字段把整页打挂），而 `13.11` **仍旧报 `6001`**。
   - ⇒ 用户会看到「详情页没有参考金额 → 点了按钮报错」这个组合。见 §4.4。
10. **`estimatedAmount` 是 5 分钟向上量化的参考快照**，契约明写**禁止渲染为应付锁定价**（`API:1019-1025`，承 `02` §1.8）。
    - ⚠️ **`TIMEOUT` 单上它仍在累积**：`BillingServiceImpl.estimatedAmount` :64-77 **只在 `IN_PROGRESS`** 上收敛到定格值；`TIMEOUT` 继续按现算增长。见 §5.3。
11. **`awaitingPickup()` = `{IN_PROGRESS, TIMEOUT}`**（`OrderStatus.java:22`），`TIMEOUT` 是**终态且不回迁** —— 补缴取件后**维持 `TIMEOUT`**，只是补录 `endAt`（`API:1070` 规则 4、`OrderStatus.java:9`）。
12. **全免单（应付 0）仍落一张 0 元 `SUCCESS` 支付单 + 0 元 `INCOME` 流水**（`API:1083`）—— 否则「已支付待取件」无从判定（承 `02` §7）。

## 2. 一期渠道形态：纯模拟按钮

**裁决：`13.11` 直接调用，不套 `wx.requestPayment` 壳。**

- 「支付并开门 / 取件开门 / 补缴并开门」点下去 = **一次 `13.11` 调用**（§3.1）。
- **不做**任何「正在拉起微信支付」的过场、不做假的收银台、不做假的 `prepay_id`。

**理由**：一期 `13.11` **同步成功**（§1.1），调用返回时交易已完成 —— 没有任何异步等待可供收银台表演。硬套壳会让壳里的「取消支付」变成**谎话**：用户以为取消了，实际上钱已扣、指令已发、门已开。**诚实的模拟按钮比会撒谎的壳安全。**

### 2.1 二期切真实支付时的改动清单（票面要求的迁移收口）

一期省下的代价 = 下面这份清单就是**二期的全部活**。改动集中在**后端契约**，C 端是随之而来的适配：

| # | 改动点 | 一期现状 | 二期形态 | 归属 |
|---|---|---|---|---|
| 1 | `13.11` 语义 | **同步完成**（调用即扣费+发指令） | 改为**创建预支付单**并返回拉起参数（`prepay_id` 等） | 后端 |
| 2 | 支付结果通道 | 无需通道 | 新增 **`/api/app/v1/pay/notify`** 回调（**二期预留路径已存在**，鉴权豁免 + 验签，`API:1072`） | 后端 |
| 3 | 拉起收银台 | **不存在此步骤** | 新增 `wx.requestPayment(prepay_id)` 调用 | C 端 |
| 4 | 失败与取消分支 | **不存在**（§4.1） | 新增：用户取消 / 支付失败 / 回调超时 —— 各需界面表现 | C 端 |
| 5 | 支付确认的等待 | **无**（同步返回即成功） | 新增：拉起后**结果未知**，需轮询订单状态直到 `paid` 落地 | C 端 |
| 6 | 按钮文案与进行态 | 同步、瞬时（只需防抖，§3.3） | 分为「点击 → 拉起中 → 确认中 → 成功/失败」多段进行态 | C 端 + T1 |
| 7 | `channel` 展示 | 恒 `MOCK_WECHAT`（**不渲染给用户**，§6.3） | 变 `WECHAT`，仍不渲染渠道名 | — |

> ⚠️ **一期唯一必须做对、否则二期返工的事**：§7 的**移交点**不能把「支付成功」与「门已开」当成同一件事。一期的同步成功很容易诱使实现者写成「调完就宣布成功」；二期的结果必须经回调 + 轮询才落地，届时这个写法会整段作废。

## 3. 动作模型

### 3.1 一个按钮，按状态换文案（承 `02` §6）

| 订单状态 | 派生条件 | 按钮文案 | 点击后 |
|---|---|---|---|
| `IN_PROGRESS` | `payAmount === null` | **支付并开门** | `13.11` → 现算应付 → 支付 → 发指令 |
| `IN_PROGRESS` | `payAmount !== null` | **取件开门** | `13.11` → 幂等分支：不重复扣费、**重发**指令 |
| `TIMEOUT`（`endAt == null`） | 无论已付多少 | **补缴并开门** | `13.11` → 补缴差额（下限 0）→ 发指令 |
| 未存入 / 已终局 | — | **无此按钮** | 调 `13.11` 只会得到 `3002` |

- **三者调同一个端点 `13.11`**，走同一个事务。**不拆按钮**（`02` §6.3）。
- ⚠️ `TIMEOUT` 行**不区分已补缴 / 未补缴**（承 `03` §5 刻意不二分）：`payAmount` 只是过去某刻的定格，客户端判不出欠不欠。文案一律「补缴并开门」，具体收多少由服务端在 `13.11` 时刻定。

### 3.2 支付前金额的展示

**裁决：进页面就显示参考金额；金额单独一行 + 「参考」二字；按钮不承载金额。**

- 展示来源**只能**是 `estimatedAmount`（`13.9`/`13.8`）—— `payAmount` 要支付成功后才定格（§1.5）。
- 措辞必须含「**参考**」：它是 5 分钟向上量化的快照，**实扣以支付时刻服务端现算为准**（承 `02` §6.2、`API:1019-1025`）。
- **支付成功后**改用 `payAmount` 显示**实付**，并明说以实付为准（§6.2）。

### 3.3 重复支付防呆：只做技术性防抖

**裁决：请求进行中禁用按钮（防连点），其余完全依赖服务端幂等。不做任何本地业务防呆。**

- **禁止**「本地判断这单已付过 → 不发请求」这类逻辑。它有两个病：
  1. **双源真相**：本地快照与 `status`/`payAmount` 分叉（承 `04` §5 第 1 条，同一病）。
  2. ⚠️ **有害**：本地拒绝发请求时，恰好**掐死「重发指令」这条唯一重试路径** —— 一个指令 `EXPIRED` 的用户会被本地状态**永久挡在门外**（`02` §6.1：重试入口就是同一个按钮）。
- 重复调用 `13.11` 的代价是零（幂等，§1.7），收益是重试能力。**这个交换必须做。**
  - ⚠️ **就地补正（2026-09-22，P1 #12 收口）**：上句对**账**成立，对**物理世界不成立** —— `DeviceCommandServiceImpl.createOpenCommand` 是**无条件 `insert`**，没有任何「已有 `PENDING`/`SENT` 指令就跳过」的守卫（源码核实）⇒ **重复调用不会重复扣费，但会真的再开一次门**。准确表述：**「账务代价为零，物理代价是再开一次门；这个交换仍然值得做，因为它是指令 `FAILED`/`EXPIRED` 之后唯一的重试路径。」** 本节的**结论不变**（仍要做重试、仍不做本地业务防呆），只是理由要讲准。见 `docs/spec/08-waiting-state.md` §7。

## 4. 异常分支矩阵（无空行）

### 4.1 「支付失败」一行：一期不存在

⚠️ **重写票面前提**：一期**没有**支付失败分支（§1.1，`API:1071` 明写「不模拟失败分支」）。矩阵里不设这一行 —— 设了就是永久空行。

一期**真正**的失败形态只有**网络不确定性**：

| 情形 | 界面表现 | 用户动作 | 说明 |
|---|---|---|---|
| 请求**超时 / 断网**（结果未知） | 提示「网络异常，请重试」 | **重试即安全** | 不知道成没成功 —— 幂等保证重试不会重复扣费（§1.7）。**既不许谎称成功，也不许谎称失败** |
| 用户**中途退出**（未发请求） | 无（什么都没发生） | 重新进入照常可付 | 订单停在**未付清、仍可支付** |

### 4.2 支付成功、但开门指令失败或过期

| 情形 | 界面表现 | 用户动作 |
|---|---|---|
| 指令 `FAILED` / `EXPIRED` | **由 P1 等待态承载**（§7）—— D6 不重复定义 | **再点同一个按钮** = 重调 `13.11` = 重发指令（§1.7） |

- ⚠️ **不得**渲染「门已开」「取件成功」：一期 `openCommandIssued` 恒真，证明不了任何事（§1.4）。
- 唯一能证明门真的开了的证据是 **`DOOR_CLOSED` 驱动的状态推进**（承 `02` §8）。

### 4.3 支付成功、但用户没关门

| 情形 | 界面表现 | 用户动作 |
|---|---|---|
| `DOOR_CLOSED` 未回执 | 详情页回落到**正常态**：`IN_PROGRESS` + 已付清 → **待取件** | 回来再点「取件开门」即可 |

- **不引入新显示态**。`03` 已裁 11 枚举 → 9 显示态，且 `03` §2 反对客户端自造与枚举错位的语义。
- ⚠️ **C 端根本不知道门关没关**：`openedNotClosed` **不在 C 端契约**（R3 登记的漏报项）⇒ 硬造「已支付未关门」需要一个不存在的字段。**这是有意的不表达，不是漏做。**

### 4.4 `6001` 费率未配置（**本文新登记的缺口**）

| 情形 | 界面表现 | 用户动作 |
|---|---|---|
| 费率未配置 | ① 详情页**没有参考金额**（`estimatedAmount === null`，展示路径吞掉，§1.9）<br>② 点按钮 → 报 `6001` 时**事后解释**：「当前费率未配置，请联系客服」 | 联系客服 |

- **不置灰按钮**（承 `04` §3「一律事后解释、绝不事前阻断」）。
- ⚠️ **不能用 `estimatedAmount === null` 反推费率没配**：未存入、已终局、以及 `6001` **都会是 `null`**（`estimatedAmount` 源码 :64-71 两个早退分支）⇒ 用它置灰会**误伤**。
- 这是**运营事故**（管理端没配费率），不是用户能修的事，出路只有客服。
- ⚠️ **登记为上线前置项**（类比 `04` §9 的「后台须配客服」）：**上线前必须确认费率已配置**，否则**所有取件都走不通**。

## 5. `TIMEOUT` 补缴

### 5.1 入口：还是同一个按钮

**裁决：`TIMEOUT` 用**同一个**按钮，仅换文案为「补缴并开门」。**

- **不新增第二个「补缴」按钮**：两种按钮调的是**同一个端点**、**同一个事务**（§3.1）⇒ 并列是给用户一个**假选择**（承 `02` §6.3）。
- 准入由 `02` §7 的「能不能取件 = `pickupCode !== null`」闸门覆盖（该口径与 `13.11` 准入同源）。

### 5.2 补缴金额由服务端定

- 补缴额 = `max(0, 现算应收 − 累计已付)`（`PaymentServiceImpl.outstanding` :107-109）。
- ⚠️ **客户端不许自己算差额**：承 `03` §5 —— `estimatedAmount > payAmount` 的派生**已被否决**（5 分钟向上量化，边界会误报）。

### 5.3 「参考金额」在 `TIMEOUT` 单上是**增长的**

- `estimatedAmount` 只在 `IN_PROGRESS` 上收敛到定格值，**`TIMEOUT` 继续累积**（§1.10）。
- ⇒ 文案必须让它**不像锁定价**（「参考」二字在此处是硬要求，不是修饰）。

## 6. 金额展示的一张表（写死口径）

### 6.1 支付前

| 字段 | 用不用 | 说明 |
|---|---|---|
| `estimatedAmount` | ✅ **唯一来源** | 参考快照，带「参考」二字 |
| 订单 `payAmount` | ❌ | 未支付时为 `null`，无值可显示 |

### 6.2 支付后：「实付」用**订单字段** `payAmount`

**裁决：详情页常驻展示用订单字段 `payAmount`（累计实收），标签叫「已付」。**

- **理由**：订单字段**幂等可重复读取**（`13.8`/`13.9` 都返回），响应值只存在于那一次调用的瞬间 —— 用它则**页面刷新后信息就丢了**。
- ⚠️ **标签只能是「已付」，不能是「已付清」**：在 `TIMEOUT` 单上 `payAmount` 只是**过去某刻的定格**（§5.3），断言「已付清」就是谎（承 `02` §7 的 D3 补正）。
- `13.11` 响应里的 `payAmount`（本次支付额）**只用于支付成功那一刻的即时反馈**（「本次支付 ¥X」），不作常驻展示。

### 6.3 全免单（应付 0）

**裁决：与其他单**完全同流程**，界面不做任何特判。**

- 全免单在契约上就是一次**正常支付**（0 元 `SUCCESS` 支付单，§1.12），按钮照常叫「支付并开门」，点击照常成功、照常开门。
- ⚠️ **「免费取件」这类特判在支付前无法实现**：免不免单取决于优惠，而优惠在**支付时刻现算** —— 支付前客户端拿不到「会不会免单」。所以 B 选项不是「更好的文案」，而是**做不到**。
- ⚠️ 唯一展示细节：支付成功后若 `payAmount === 0`，**别渲染「支付成功 ¥0.00」**这种怪话，说「本次无需付费，已开门」。（最终措辞归 T1。）

## 7. 与 P1 的衔接点（票面要求的接口定义）

**移交点 = `13.11` 响应到达即移交。**

```
[详情页取件区块]  点「支付并开门 / 取件开门 / 补缴并开门」
        │
        └─ POST /orders/:id/pay  {}          ← D6 的职责到此为止
                │
                ├─ code == 0 → 拿 { orderStatus, paid, payAmount, paidAt }
                │        └─→ 立即移交 P1「等待关门」等待态       ← 移交点
                └─ code != 0 → 就地解释（3002 / 8003 / 3001 / 6001，§4）
```

**D6 交给 P1 的东西**：`{ orderStatus, paid, payAmount, paidAt }` —— 仅此四项。**D6 到此结束**。

**P1 接手的东西**：轮询策略、等待态界面、指令 `FAILED`/`EXPIRED` 的界面与措辞、防连点、超时未关的呈现。

五条**必须写死的约束**：

1. ⚠️ **移交后不得再渲染支付界面** —— 不得出现第二个「支付」按钮或「再次支付」入口。重试的本质是**再调一次 `13.11`**（§1.7），入口就是同一个「取件开门」（`02` §6.1）。
2. ⚠️ **等待态只能说「已发出开门指令」**，不许说「门已开」（§1.4，`02` §8）。
3. **移交的依据是 `code == 0`**（支付成功），不是 `paid` —— ⚠️ 一期 `paid` 与 `openCommandIssued` **都写死 `true`**。
4. **`orderStatus` 移交后仍是 `IN_PROGRESS`/`TIMEOUT`**（不是 `COMPLETED`，§1.6）——等待态的推进靠轮询到状态变化，不靠这个初始值。
5. **转单路径复用同一移交点**（承 `05` §4.2）：`13.15` 转单后直接进同一等待态组件，但 ⚠️ 转单路径**没有 `13.11` 的响应**（`05` §4.2 已记：不能说「请在 N 分钟内放入」）。

## 8. 刻意不做（避免被当成漏做）

- 不做 `wx.requestPayment` 壳、不做假收银台、不做假 `prepay_id`（§2）。
- 不做本地「这单已付过」的业务防呆（§3.3）。
- 不做「支付失败」分支（一期不存在，§4.1）。
- 不做「已支付未关门」显示态（无字段，§4.3）。
- 不新增第二个「补缴」按钮（§5.1）。
- 不用 `estimatedAmount` 判欠费、不用 `payAmount > 0` 判付清、不用 `estimatedAmount === null` 判费率未配（§4.4、§5.2、`02` §7）。
- 不给全免单做特判文案（支付前不可知，§6.3）。
- 不渲染渠道名（`MOCK_WECHAT` 是内部概念）。
- 不做退款入口（一期仅全额、二期，且**退款入口不在本 effort 内** —— 票面边界）。
