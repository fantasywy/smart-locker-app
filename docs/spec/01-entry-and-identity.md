# 01 信息架构 / 入口与身份

> 承载 ticket：**D1（#5）**。契约源：`java/smart-locker/docs/API设计文档.md` v1.0 —— 用户端 **§13**、错误码 **§15**、契约增量 **§16**。本文只写口径，不写实现代码。
> 命名约定：`docs/spec/NN-<topic>.md`，编号即阅读顺序，后续 D 票顺延取号。

## 1. 前提事实（实现者必须知道，否则下面的裁决看起来像任意选择）

1. 用户端 16 个端点里**只有 `13.1 POST /auth/login` 与 `13.2 POST /auth/refresh` 免鉴权**（§13 开篇 + §16 #29）。**未登录时后端不提供任何业务数据** —— 没有柜机、没有订单、没有预约、没有积分。
2. **没有「站点列表 / 附近柜机」端点**。`lockerId` 的唯一来源是 `13.6 GET /lockers/by-code?code=<柜机码>`。
3. 需要 `lockerId` 的动作只有两个：`13.7 创建存件订单`、`13.12 创建预约`。取件（`13.9` / `13.11`）按 `orderId`、预约到点使用（`13.15`）按 `reservationId`，**都不需要 `lockerId`**。
4. `13.1` 首次出现 openid **自动注册**（初始 `score.max`、状态 `NORMAL`）；**黑名单用户允许登录**（`status = BLACKLISTED`）。⇒ **不存在「登录被拒」的业务分支**。
5. `wx.login` 无感，`openid` 静默可得。`wx.getUserProfile` 自 2022-11-08 24:00 起被收回（一律返回灰色头像 + 「微信用户」），取真资料只能用「头像昵称填写能力」，那是**用户主动填写**、不是一次授权。

**推论**：「未登录态」在 C 端不是一个可展示的状态，只是一个过渡态。

## 2. 入口

### 2.1 柜机码与载荷格式

柜机二维码的载荷**统一为 URL**：

```
https://<域名>/l/{lockerCode}
```

`lockerCode` 即 `13.6` 的 `code` 参数（如 `WD-01`）。

### 2.2 两条扫码通道（都要做）

| 通道 | 用户动作 | 进入方式 | 前端拿到的东西 |
|---|---|---|---|
| **A** 微信「扫一扫」直达 | 在小程序**外**扫柜机码 | 冷启动，落到后台配置的功能页面 | `onLoad(q)`，`q` = 完整链接的 URL 编码，需 `decodeURIComponent` 一次；另附 `scancode_time` |
| **B** 小程序内扫码 | 已打开小程序，点首页「扫码存件」 | 热启动，叠在当前页面栈之上 | `wx.scanCode` 的 `result` |

**三来源收敛**：`q` / `options.code` / `scanCode.result` → `resolveLockerCode()` → `code`。
**页面只认 `code`，不关心来源** —— 「用户从哪进来」这个变量在收敛之后从产品里消失。

> `scancode_time` **不参与任何业务判断**：柜机二维码是静态贴纸，时间戳没有语义。

### 2.3 页面骨架

```
tabBar
├── 订单（默认首页）   ← 订单列表；顶部常驻「扫码存件」入口
└── 我的               ← 资料 / 积分 / 积分明细 / 计费说明 / 常见问题 / 联系客服

非 tab 页面
└── 柜机页             ← 扫码落地页（外部扫一扫进入时栈深可能为 1）
```

- **首页 = 订单列表**：回访场景（取件码、超时费、进行中订单的状态推进）才是最高频的打开动机。
- **扫码是动作、不是目的地**：不做成 tab。一次 `wx.scanCode` 即跳走，取消后页面空白；且 tabBar 的选中态对动作型入口是语义错误。
- 首页顶部提供**常驻**「扫码存件」入口，覆盖「先打开小程序、再走到柜机前」这条通道（通道 A 完全不经过首页，所以首页不需要为它让位）。

### 2.4 柜机页的出口

通道 A 是**冷启动、页面栈深度 1**，系统返回 = 直接退回微信；而柜机页是非 tab 页、**底部 tabBar 不显示**，屏幕上没有任何通往订单列表的可见路径。因此柜机页**顶部固定一个「我的订单」出口**（`wx.switchTab` 到订单 tab）。

两条通道表现一致，**不按进入来源分叉**（用户不关心自己是从哪进来的）。

## 3. 登录

### 3.1 闸门形态

**隐式前置登录**：冷启动即 `wx.login` → `13.1` → 拿到 `accessToken` 后渲染业务数据。

**一期不设「登录按钮」概念。** 理由：`wx.login` 无感，且登录是唯一的数据闸门 —— 把它做成用户可见的动作，等于给用户增加一个没有回报的决策点。

### 3.2 冷启动表现

- 页面**结构先出现**（骨架屏），数据区等 token。
- **不做本地业务数据缓存**：取件码与订单状态属「看到就必须是真的」的数据；缓存说谎（用户拿着过期取件码走到柜机前）比空白更糟。**首屏加速靠骨架屏，不靠数据缓存** —— 这两件事常被混为一谈。
- 登录失败 → 走 §4 的**全局唯一失败出口**。

> 附注（假设，非 D1 裁决）：本文假设 token 持久化到 storage（`access` 2h / `refresh` 30d，若不持久化则有效期设置没有意义）。**定稿权在 D7（#11）**。若 D7 决定不持久化，冷启动简化为 `wx.login → 13.1`，§3.3 的 `401+2005` 分支就只在会话内出现。

### 3.3 登录失效与请求重放

| 触发 | 行为 |
|---|---|
| `401 + 2001`（access 无效） | 用 refresh 静默刷新**一次**，然后重放原请求 |
| `401 + 2005`（refresh 失效） | 清登录态 → `wx.login` **自动重登一次** → 重放原请求 |
| 重登也失败 | **丢弃原动作**，进 §4 的失败出口。**不做后台补发** |

两条硬口径：

1. **重放是安全的，写请求也重放。** 401 由鉴权拦截器在业务逻辑**之前**返回 ⇒ 请求**未被服务端执行**，重放不构成重复提交（建单 `13.7`、取消 `13.10`、支付 `13.11`、建预约 `13.12` 同理）。
   真正「可能已生效但响应丢失」的场景是**网络超时**，不是 401 —— 那条分支应通过读接口核对状态，**不靠重放**。
2. **重登也失败时绝不后台补发。** 否则会出现「用户点了确认支付 → 网络断 → 用户离开 → 半小时后自动扣款」。宁可让用户回来手动重试（`13.11` 幂等，重试安全）。

**约束（交给 D7 请求层实现）**：同一时刻只允许**一次**登录失效处理 —— 并发 401 不得触发多次刷新 / 重登（单一飞行 + 排队重放）。

### 3.4 登录态状态机

```
启动
 └─ 有 refresh token？ ──无──→ [静默登录 wx.login → 13.1]
                          └─有─→ 带 access 发请求
                                    ├─ 2xx ──────→ [已登录]
                                    ├─ 401+2001 ─→ 刷新一次 → 重放
                                    │                └─ 再失败 ─→ [清态重登]
                                    └─ 401+2005 ─→ [清态重登]
 [清态重登] = wx.login → 13.1
      ├─ 成功 ─→ 重放原请求 → [已登录]
      └─ 失败 ─→ [全局失败出口]（丢弃原动作，不补发）
```

## 4. 全局失败出口

**只有一个**，由启动态驱动，**不下放到各页面的数据区**。否则同一分支被复制 N 次，且会出现「有的页能重试、有的页不能」的不一致。

内容：说明 + 重试 + 静态出口（计费说明 / 常见问题 / 联系客服 —— 与 §5 同一份内容，两条路一份内容）。

登录失败的成因可穷举：网络不通 / `wx.login` 失败 / `13.1` 返回 `8001`（code 无效）/ 后端 5xx。

## 5. 「我的」页

| 区块 | 内容 | 来源 |
|---|---|---|
| 资料 | 昵称 + 头像，**用户自愿填写** | `13.4 GET /profile` / `13.5 PUT /profile` |
| 积分 | `score` | `13.4` |
| 积分明细入口 | 分页列表（呈现形态由 D4 #8 收口） | `13.16 GET /score-logs` |
| 静态出口 | 计费说明 / 常见问题 / 联系客服 | 本地内容，不要后端 |

- **昵称头像用「头像昵称填写能力」**（`button open-type="chooseAvatar"` + `input type="nickname"`，基础库 ≥ 2.21.2），**入口只在这里**，不阻塞任何流程。平台官方最佳实践即「可在个人中心或设置等页面使用该能力」。
- **手机号一期不做**：后端没有换绑端点，`nickname/avatar/phone` 只在**首次注册**时落库 —— 用户换号后该字段会一直撒谎，展示它比不展示更糟。
- **不做「退出登录」**（`13.3 POST /auth/logout` 存在但不接）：登录身份是微信 openid，用户无法在小程序内切换微信账号，「退出登录」唯一的效果是把自己踢进一个必须立刻自动重登的状态。**有意不做，不是漏做。**
- ⚠️ 待复核（不占决策）：联系客服的载体 —— `open-type="contact"` 客服会话，还是直接展示电话 / 微信号，取决于小程序主体与后台客服配置。
- 「预约列表挂在哪」由 **D5 #9** 裁决；黑名单 / 低信用分的可见性由 **D4 #8** 裁决。**本页骨架须同时容纳两方的结论。**

## 6. 柜机页

- **上下文 = 页面参数**：`onLoad` 解析出的 `code` 就是全部上下文，不持久化、不跨页共享。
- **禁止隐式记住上次柜机**：不得把柜机上下文写入 `storage`。最坏结果是用户在**另一台**柜机前被带上别的柜机的上下文，下单成功而门在别处开了 —— 省一次扫码的收益与开错柜门的风险严重不对称。
- 渲染后调 `13.6` 取柜机信息：`siteName / position / online / status / cellAvailability{small,medium,large}`。
- ⚠️ `13.6` **不返回价格、不返回格口清单**（`cellNo` 只在建单后返回），所以本页天然只有一屏：站点名 + 位置 + 三档余位 + 「开始存件」。

### 6.1 非正常进入

| 情况 | 性质 | 表现 |
|---|---|---|
| 解析不出 `code` | 入口失效 | 「这个码没用」页，提示用微信扫柜机上的码；出口 = 重新扫码 + 我的订单 |
| `13.6` → `1002`（柜机不存在 / 已软删） | 入口失效 | **同一个页面**，文案换为「可能是旧贴纸」+ 引导联系客服 |
| `online = false` / `status = FAULT｜MAINTAINING｜OFFLINE` | **正常响应** | **完整渲染柜机信息**，不可用入口**置灰并写明原因** |
| `cellAvailability[type] === 0` | **正常响应** | 该类型入口**置灰**（建单会 `8002`），说明「该规格已满」 |

`§16 #29` 明确：`online=false` + 余位 0 是**正常响应而非错误**，后端建议「小程序选柜页按 `online` / `cellAvailability` 置灰入口」。把这两种做成错误弹窗，等于把后端声明的正常响应当异常处理，用户会以为自己扫错了。而「拿到数据」意味着用户能看见「确实有这么台柜机、只是现在不能用」，这是有效信息。

**余位 0 时不得引导「去预约」**：预约同样只认 `FREE` 格口（`13.12` 无空闲 → `8002`），唯一真出口是「换一台柜机」。

## 7. 上线前置（不在本 effort，必须显式登记为依赖）

通道 A 依赖以下**四条全部满足**；缺任一条，退化为只有通道 B（必须先打开小程序再扫）：

1. 小程序主体为**企业 / 媒体 / 政府及其他组织类型** —— **个人主体不支持**该功能。
2. 二维码规则所用域名已完成 **ICP 备案**。
3. 校验文件可访问：`https://<域名>/l/<校验文件名>`（放在规则 URL 的最后一级子目录）。
4. **小程序已有线上版本** —— 微信要求先发布代码，才能发布二维码跳转规则。

后台配置：**一条**前缀规则 `https://<域名>/l/`（以 `/` 结尾以启用子路径匹配；单账号上限 500 条，我们只用 1 条）。

## 8. 刻意不做（避免被当成漏做）

- 不做柜机浏览 / 搜索 / 附近柜机 —— 后端无此端点，且已作为跨仓库共识写入 **ADR-0001**。
- 不做「登录按钮」，不做「退出登录」。
- 不做本地订单 / 预约数据缓存。
- 不做首登欢迎页 / 新手引导：`13.1` 首登自动注册对用户不可见，首次进入 = 空订单列表（**空态由 D3 #7 裁决**）。
- 不展示手机号。
- 不用 `scancode_time` 做时效校验。
