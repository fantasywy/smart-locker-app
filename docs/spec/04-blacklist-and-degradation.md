# 04 黑名单与降级（受限态与准入类异常）

> 承载 ticket：**D4（#8）**。契约源：`java/smart-locker/docs/API设计文档.md` v1.0 —— 用户端 **§13.1 / §13.4 / §13.6 / §13.7 / §13.10 / §13.11 / §13.12 / §13.15 / §13.16**、错误码 **§15**；需求 **§4.8**（信用积分与黑名单联动）。事实源：`BlacklistServiceImpl` / `ScoreServiceImpl` / 各 `……ServiceImpl` 的校验序。
> 本文只写口径，不写实现代码。上游：`docs/spec/01-entry-and-identity.md`（§2.3 骨架、§5「我的」页）、`docs/spec/02-c-end-device-boundary.md`（§9 屏端九态对齐、§10 取件兜底）、`docs/spec/03-order-list.md`（§8 异常浮现、§10 登记项、§12 留位）。

## 1. 前提事实（实现者必须知道，否则下面的裁决看起来像任意选择）

1. **`5004` 的拦截面恰好是 3 个动作**：`13.7` 创建存件订单、`13.12` 创建预约、`13.15` 开始使用预约（`API设计文档.md:64`、`:1295`「用户端下单/创建预约/开始使用」；需求 `:134`）。服务端 `message` 原文 =「**黑名单用户禁止该操作**」。
2. ⚠️ **`13.11` 支付不被 `5004` 拦**。直接核 `:1057-1084` 的规则 1–4，只列 `3002 / 8003 / 3001 / 6001`。同理 `13.10` 取消、`13.4 / 13.8 / 13.9 / 13.13 / 13.14 / 13.16` **也都不拦**。
   ⇒ **受限只封「开新动作」，不封「收尾动作」。** 票面「能看不能做」的准确表述是「**能看、能做完手上的、不能开新的**」。
3. **校验序（决定用户撞见哪个码）**：
   - `13.7` = `5004 → 4004 → 8002`
   - `13.12` = `5004 → 4004 → 8002 → 8006 → 8007`
   - `13.15` = **`5004` 判在 `8003`（归属）之前**（`:1129`）
   - ⇒ `5004` 会**遮蔽**它后面的一切原因（`4004 / 8002 / 8003 / 6201 / 6202 / 8006 / 8007`）。一个既被拉黑、预约也过期的用户，收到的只有「受限」。
4. **C 端的 `blacklistRecord` 只有三个字段**：`{ reason, createdAt, auto }`（`:956`、`:959`）。管理端 9.4 才有 `releaseCondition`（`:581`）⇒ **C 端说不出解除条件，也算不出剩余天数**。
5. ⚠️ **C 端拿不到任何一个配置数字。** `score.blacklistThreshold`(60) / `score.autoRemoveDays`(30) / `score.timeoutDeduct`(5) / `score.noShowDeduct`(10) / `score.max`(100) / `reservation.holdMinutes`(15) / `reservation.noShowMinutes`(30) / `reservation.maxHours`(24) 全是可配参数（需求 `:305-316`、管理端参数端点 `:864`），而 **C 端 16 个端点里没有任何参数查询**（R1 §5 + §13 全文）。**唯一例外**：`13.7` 响应回显的 `openTimeoutMinutes`（建单响应 `CreateOrderVO`）。
6. **自动拉黑在积分明细里留痕，且 `reason` 服务端原文自带阈值数字**：需求 `:231` 明写「自动进入黑名单（**在积分明细留痕**）」；API `:626`、`:633` 给出形如「**积分低于黑名单阈值（60）**」的自动原因文案。⇒ 不脱敏就会从**两个地方**泄露 60。
7. **`auto=false`（人工拉黑）的 `reason` 是管理端自由文本**，只校验「必填/非空白」（`:607`），**无长度约束**。
8. **扣分触发点全表**（需求 `§4.8`）：订单超时结束（`TIMEOUT` 生成时，−5）/ 预约爽约（`NOSHOW` 生成时，−10）/ 恶意占用（−10，一期预留、管理端人工认定）/ 管理端手动调整（±，须填原因）。初始分 = `score.max` = 100。
9. **`13.16` 积分明细的真实字段形状**（`API设计文档.md` §9.3 `:588-596`，用户端 `:1135` 明写「结构同管理端 9.3」）：`{ id, delta, reason, type: AUTO|MANUAL, operatorName, createdAt }` + `total`。
10. **`4004` / `8002` 与 `5004` 同在一张校验序表上**，且在收口前**没有任何一张票认领过它们的表现**（`03` §12 与 `01` §7 的留位清单里都没有）。
11. **被拒动作无副作用**：`13.7` / `13.12` / `13.15` 的失败整体回滚、不留半成品占用（`:1353` #25①）⇒ 被拦不产生任何需要清理的对象。

## 2. 术语（承 `CONTEXT.md`）

| canonical | 含义 | `Avoid` |
|---|---|---|
| **受限** | 用户可见的账号级状态：账号处于限制中，不能开新动作 | 封号、被拉黑、禁止操作 |
| **信用分** | `score`。扣减型的**行为约束**分，不是可兑换的消费积分 | 积分、评分、分值 |
| **单笔校验被拒** | 某一笔动作因该笔自身条件不成立而未通过（`3002` / `6201` / `6202` / `4004` / `8002` …） | 与「受限」混用 |

- **「黑名单」保留为后端字段概念**（`status = BLACKLISTED` / `blacklistRecord`），**不进用户文案** —— 它自带「你被列入名单」的污名感，而真实状态是可自动解除的。
- ⚠️ **「受限」与屏端「业务拒绝」必须显式分开。** 屏端那三个码（`9001 / 9002 / 9003`）是**单笔校验被拒**，与账号是否受限无关（`02` §9）。用户极易把屏上的拒绝理解成「我被封了」，文案上要能一眼区分。

## 3. 承载模型：只在「我的」页常驻 + 动作点就地解释

**不挂全局横幅。**

| 位置 | 表现 |
|---|---|
| 冷启动 / 登录（`13.1` / `13.2`） | **无差别** —— 响应带 `user.status`，但**不据此提前拦截**（见 §5） |
| 首页顶部常驻「扫码存件」入口 | **不变**（这就是 `03` §12 留问「是否影响下单入口」的答案：**不影响**） |
| 订单列表行 | **不变**，**不加任何受限标记**（承 `03` §8：异常归状态本身，不做页面级横幅） |
| 订单详情 · 取件区块 | **动作全可用** + 一行提示（§6） |
| 扫码 → 柜机页（`13.6`） | **不变**，可正常查柜机与余位 |
| 柜机页「存件」（`13.7`） | 保持可见可点 → `5004` → **专用解释** |
| 预约创建提交（`13.12`，界面位置归 D5） | 可点 → **同一份**解释 |
| 预约「开始使用」（`13.15`，界面位置归 D5） | 可点 → **同一份**解释 |
| 「我的」页 | 积分行常驻；受限时**插一张受限卡**（§4） |
| 信用分明细页 | **不变**（可正常查看，含扣分留痕） |

理由：后端的设计意图本就是「能看不能做」，挂全局横幅会把一个**其实还能正常用**的 App 渲染成「你被封了」，并持续污染一个完全正常的订单列表页。`13.4 profile` 的真实落点本来就是「我的」页。

## 4. 「我的」页

```
资料       昵称 + 头像（用户自愿填写）
信用分     88 · 状态语义一行        ← 常驻，NORMAL 时也显示
┌─────────────────────────────┐
│ 受限卡（仅 status = BLACKLISTED 时插入）        │
└─────────────────────────────┘
信用分明细 →                        ← 独立页（§7）
静态出口   计费说明 / 常见问题 / 联系客服
```

### 4.1 受限卡的构成

| 段 | 内容 |
|---|---|
| 解释 | 走 §5 的 `auto` 分叉文案（**映射，不直出阈值数字**） |
| 时间 | 「限制开始于 `createdAt`」 |
| 清单 | 「以下动作暂时不可用」：存件 / 创建预约 / 开始使用预约 |
| 反例交代 | 「**已存入的订单不受影响，仍可正常取回**」 |
| 出口 | 联系客服（§8） |

- `auto=false` 时 `reason` 是管理端自由文本、**无长度约束** ⇒ **折叠 3 行 + 可展开**，避免一条长原因把整页撑变形。
- **不显示**：剩余天数、解除日期、阈值、还差多少分 —— C 端拿不到这些值（§1.5）。

## 5. 事前阻断 vs 事后解释：**一律事后**

冷启动的 `13.1` 响应就带 `user.status`，所以 C 端**从第一屏起就知道**用户是否受限。**仍然不据此提前拦截**：

1. **拦截权只能属于服务端。** `status` 是登录时刻的快照 —— 解除后、刚被拉黑时都可能过期。本地阻断会造出「本地说不让、服务端其实让」的**双源真相**，会把**已经解禁的用户挡在门外**，这是最坏的一类 bug。
2. 用户已经站在柜机前，预防提示**省不掉路程，只省一次点击**。
3. 一份文案、一个 guard：与 §3 的单一口径一致。

**推论：柜机页也不挂预防性提示。** 本次不做本地 `status` 快照（承 `01` §3.2「不做本地业务数据缓存」。

### 5.1 统一解释文案（三个被拦动作共用一份）

**动作点就地解释**（弹层或页内区块）：

> **账号暂时受限**
> 因{\<受限原因\>}，账号已被限制，暂时无法{\<存件 / 创建预约 / 开始使用预约\>}。
> **已存入的订单不受影响，仍可正常取回。**
> 如需了解，请联系客服。

- 「**保持可见、可点、点击后解释**」——**不置灰、不隐藏**。置灰不给原因只是裸错误码的变体；隐藏会让用户以为功能不存在。
- 文案里**不出现错误码、不出现「黑名单」、不出现任何数字**。

### 5.2 `5004` 必须特判，不许走通用 `message` 通道

R1 定的通用规则是「前端拦截器按 `code` 统一提示、**不硬编码文案、按 `message` 展示**」。`5004` 是**唯一例外**：

- 服务端 `message`（「黑名单用户禁止该操作」）既不解释原因、也不给出路 —— 按 `message` 直出等于把问题原样丢回用户，仍属票面验收要禁止的「裸拒绝」。
- **其余错误码一律不变**，仍按 `message` 直出。
- 这条最终要落进 **D7 #11** 的请求层职责边界：拦截器对 `5004` 不直出，改为向调用方抛出可识别的受限错误，由调用点渲染 §5.1。

### 5.3 归因纪律：只陈述受限，**不猜**更具体的原因

`5004` 遮蔽了 `4004 / 8002 / 8003 / 6201 / 6202`（§1.3）。即便本地已加载的数据看起来能推出别的解释，也**一律不猜**：

1. 归因权只在服务端；客户端**算不出**窗口（`holdMinutes` / `noShowMinutes` 拿不到，§1.5），也**算不出**余位。
2. 猜错比不猜更糟 —— 用户会按错误原因行动（去续约、去换柜机），而问题依旧存在。
3. 一旦解释有两个来源，就会开始不一致。

**代价照实记**：受限用户看到的是**一个被遮蔽过的世界**。这是后端既有的校验序造成的（`Out of scope`，不可改），C 端只能如实转述。

## 6. 存量订单的收尾权

| 动作 | 端点 | 受限时 | 额外解释 |
|---|---|---|---|
| 取件开门（未清账先清账 / 已清账重发指令） | `13.11` | **可用** | 无 |
| 取消（仅「待存入」时出现） | `13.10` | **可用** | 无 |

- **收尾动作全集 = 取件开门 + 取消**，两者后端都不禁（§1.2）⇒ **都保持正常可用，且都不额外解释**（能用就不提示，反常提示反而让用户以为要出事）。
- 详情页**取件区块**在受限时补**一行**：「账号受限不影响取回本单」。与 `02` §10 已定的客服出口**并置**，**不新增第二个出口**。
- **这是本票最有价值的一条** —— 它解掉「我的东西拿不出来了」这个最大的恐慌，且完全建立在既有契约之上，不需要后端做任何事。

## 7. 信用分与积分明细

### 7.1 「我的」页的信用分行

`score` + **一行状态语义**（`NORMAL` → 中性；`BLACKLISTED` → 警示档）。**不做进度条、不做「还差 X 分」**（§1.5）。

### 7.2 规则说明的落点

「哪些行为会扣分」放在**信用分明细页顶部的一段可折叠说明**：

> **信用分怎么会变？** 订单超时结束、预约后未到店、违规占用储物格，都会扣减信用分；信用分过低会被限制使用。计费与超时规则见「计费说明」。

放这里的理由：正好在被扣分的地方，用户起疑时第一眼能看到；且**不新增 `01` §5 的静态出口项**（那份清单是 `01` 定的，且被 §4 的全局失败出口共享，加项会牵动两处）。

### 7.3 明细页版式

- `pageSize = 20` + 上拉加载，**终止条件同 `03` §7**（已加载条数 ≥ `total`）；分页越界钳制到末页。
- 每行：`delta`（**正负号显式**）+ `reason` + `createdAt`；来源标 `type`（`AUTO` → 「系统」/ `MANUAL` → 「管理员」）。
- **`operatorName` 不展示**（管理端字段，对用户无意义）。
- 颜色：**扣分（`delta < 0`）用警示 / 危险档**，加分用中性档。⚠️ **不要套用股票口径的红涨绿跌** —— 这里是「分数下降是坏事」。

### 7.4 `reason` 的分叉与脱敏（**两处共用一个判据**）

判据统一为 **`auto` / `type === AUTO`**：

| 来源 | 判据 | 呈现 |
|---|---|---|
| **黑名单记录**（§4.1） | `blacklistRecord.auto === true` | **映射脱敏**，不直出阈值数字 |
| **积分明细**（§7.3） | 明细行 `type === "AUTO"` | **映射脱敏**，不直出阈值数字 |
| 两者 | `auto === false` / `type === "MANUAL"` | **直出原文**（管理端人工填写，给人看的，直出才是尊重） |

**系统原因映射表**（覆盖面 = 需求 `§4.8` 的自动触发点全集，只有四种）：

| 服务端原文（示意） | 用户可见文案 |
|---|---|
| 积分低于黑名单阈值（N） | 信用分低于平台规则下限 |
| 预约爽约 / 预约爽约（预约单号） | 预约后未到店 |
| 订单超时 | 订单超时未取 |
| 恶意占用 / 违规占用 | 违规占用储物格 |

映射表的作用是**覆盖面**，不是逐字替换（服务端原文可能含单号等附注）。

- 定性：这是**展示层脱敏**，**不是改写历史**。后端原文一个字节都不动，C 端只决定「给用户看哪一版」。
- ⚠️ 映射表加入 `T1 #13` 的文案表，与错误码措辞同一张表。
- ⚠️ 不加**保底句式**：任何未命中的系统文案**原样展示**，不拼「可能是……」 —— 保底句式会重新引入不确定性，且与 §5.3 的归因纪律冲突。

## 8. 客服出口

- **只做 `open-type="contact"` 一个按钮。**
- ⚠️ **`open-type="contact"` 是否可用在运行时探测不到**（客服配置在微信后台，前端无法查询；未配置时点击**静默无反应**）⇒ **不做运行时切换、不做双出口**。任何「自动降级」都只是把静默失败换个地方发生，而双出口会把一次性的配置问题**永久固化成 UI**。
- **登记为上线前置项**（微信后台必须配置客服），见 §11。
- 这是取件路径**唯一的人工通路**（`02` §10），也是受限申诉的唯一出口。

## 9. 准入类异常：`4004` 与 `8002`

本票只兜**准入类**失败，**不写恢复机制**（「去哪找别的柜机」是入口侧问题，归 `01` 的扫码链路，这里只给一句引导）。

| 码 | 触发（校验序内） | 用户可见表现 |
|---|---|---|
| `4004` | 柜机不可用（离线 / 故障 / 维护中；已软删同归此码） | 「这台柜机暂时不可用，请换一台或稍后再试」 |
| `8002` | 该格口类型无空闲格口 | 「该类型格口已满，换一种类型或换一台柜机」 |

- 两者与 `5004` **共享同一个事务与同一条校验序**，分开归属会割裂同一场景的错误语义。
- 与 `13.6` 的关系：柜机非 `ONLINE` 时 `cellAvailability` 三项**恒为 0 且不报错**（R1 陷阱表）—— 那是**提交前**的禁用依据，`4004` 是**提交时**的兜底，两者不冲突也不互相替代。
- `13.6` 的 `1002`（柜机不存在 / 已软删）已在 `01` §7 定案，不重复。

> **本票边界（避免被当成漏做）**：单笔业务校验失败 —— `3002`（取消不可 / 支付不可）、`3001`、`6201`、`6202`、`8003`、`6001` —— **不在本票**，留在各自动作所在的票（详见 `03` §12 与各 D 票）。

## 10. 刻意不做（避免被当成漏做）

- 不做全局受限横幅（§3）。
- 不做**事前阻断**，不做本地 `status` 快照（§5）。
- 不置灰、不隐藏任何被拦动作（§5.1）。
- **不做解锁倒计时 / 剩余天数 / 解除日期** —— `releaseCondition` 不在 C 端契约（§1.4）。
- **不做「还差 X 分被限制」进度条 / 「再犯一次会怎样」预警** —— 阈值与扣分额都拿不到（§1.5）。**只做事后告知。**
- 不在订单列表行加受限标记（§3）。
- 不展示 `operatorName`；不展示原始错误码；**不展示任何未经服务端回显的数字**（§11）。
- **不新增申诉端点**（后端没有，不假装有）；**不改后端**。

## 11. 硬规则：C 端不得展示任何未经服务端回显的值

**判据 = 「这个值是不是服务端在响应里回显过的」，不是「它是不是配置项」。** （`openTimeoutMinutes` 也是配置项，却是允许展示的。）

| | 允许展示 | 禁止展示 |
|---|---|---|
