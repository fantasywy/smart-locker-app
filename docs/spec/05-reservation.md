> 本文只写口径，不写实现代码。上游：`docs/spec/01-entry-and-identity.md`（§6 柜机页、§5「我的」页）、`docs/spec/03-order-list.md`（§2 单流模型、§3 上浮）、`docs/spec/04-blacklist-and-degradation.md`（**§11 硬规则：不得展示任何未经服务端回显的值** —— 本文直接引用，不重新裁决）。

## 1. 前提事实（实现者必须知道，否则下面的裁决看起来像任意选择）

1. **C 端预约端点只有 4 个**，全部在 `AppReservationController`：`13.12` 创建、`13.13` 我的预约列表、`13.14` 取消、`13.15` 开始使用（转单）。**没有预约详情端点**。
2. ⚠️ **C 端拿不到任何一个预约配置数字**（承 `04` §1.5）。`reservation.holdMinutes`(15) / `reservation.noShowMinutes`(30) / `reservation.maxHours`(24) / `score.noShowDeduct`(10) / `score.blacklistThreshold`(60) **既不在任何 C 端响应里，C 端也没有参数查询端点**。
   - ⚠️ **不对称事实**：`13.7` 建单响应**会回显** `openTimeoutMinutes`（`CreateOrderVO`），**预约侧没有任何对应回显**。这条差异是 §4 / §5 只能「讲机制不讲数字」的根因。
3. **使用窗口 = `[planStartAt − holdMinutes, planStartAt + noShowMinutes)`，半开区间**（`API:1129`、`:1353`②）。窗口外或非 `PENDING` → `6202`。**两个端点 C 端都算不出**。
4. **窗口的语义**：左界 = 可**提前**开始（提前宽限）；右界 = 到期**爽约**。到达右界即判爽约，右开（恰好等于右界不可用）。
5. **`13.12` 的时段校验（`8006`）三条**（`ReservationRule:21-37`）：① `end > start`；② 时长 ≤ `maxHours`（严格大于才拒，恰好等于合法）；③ `planStartAt` **必须严格晚于 now**（立即寄存走 `13.7`）。
6. **`13.12` 无任何粒度与提前量约束**：不要求整点 / 15min 对齐，没有最小提前量，也没有「最多提前 N 天」。**这些都是 C 端自决项，后端当前不拦**。
7. **`13.12` 校验序冻结** `5004 → 4004 → 8002 → 8006 → 8007`（`API:1353`①）—— **余位先于时段**，先锁格口再看时段，失败整体回滚、不留半成品占用。
8. **`13.15` 校验序**：`5004`（**判在归属之前**）→ `8003` → `6201` → `6202`（`PENDING` + 窗口）→ `4004`（`API:1129`、`:1353`②）。
9. **`13.15` 转单不可逆**：同格口转存件订单（`IN_PROGRESS`、`startAt=null`、关联 `reservationId`）→ 预约置 `USED`（**终态**）、回填 `actualStartAt`/`orderId` → 生成 `OPEN_CELL(USER_DROP)` 指令。**关联订单被取消也不回退预约**（`API:1131`）。
10. **转单后预约不从列表消失**：`13.13` 的 `status` 可空，不传即返回全部，`USED` 行仍在（`orderId`/`actualStartAt` 非空）。只有显式传 `status=PENDING` 才隐藏。
11. **`13.13` 列表项 12 字段**（实测已核）：`id / resvNo / lockerId / lockerNo / siteName / cellNo / cellType / planStartAt / planEndAt / actualStartAt / status / orderId`。
    - ⚠️ **无 `createdAt`**。管理端 8.2 有 `createdAt` / `cancelReason` / `cancelSource` / `expireReason`，**C 端全都没有**。
    - ⇒ **C 端区分不了「用户取消」与「系统取消」**（`cancelSource` 不在 C 端契约），也**说不出取消/失效原因**。
12. **`13.13` 服务端排序 = `id DESC`**（预约创建倒序，`ReservationServiceImpl:128`；文档未定，实现如此）—— 语义上等价于「创建时间倒序」，但 **`createdAt` 本身不可见**。
13. **`13.13` 只接受单个 `status`**（五态 `PENDING|USED|CANCELLED|NOSHOW|EXPIRED`，可空），**无多值过滤**。分页越界**钳制到末页**、`pageSize` 上限 100。
14. **取消（`13.14`）前置只有 `status === PENDING`**：无任何时间限制 —— **窗口已开、甚至过了 `planStartAt` 但未到 `noShowMinutes` 时仍可取消**。成功释放格口（`RESERVED → FREE`）、**不扣分**。非 `PENDING` → `6202`。
15. **两种「没用成」的原因完全不同**：`NOSHOW` = 用户没去（**扣分**，`score.noShowDeduct`）；`EXPIRED` = 柜机/格口故障（**不扣分**，系统无责，`cancelSource=SYSTEM`）。
16. **爽约是定时任务异步置位的**（每 60s 扫一次），**C 端不会有任何主动通知**（无推送通道）。
17. ⚠️ **`13.8` / `13.9` 都不返回 `reservationId`** —— 订单侧**无法**反查来源预约；**只有预约 → 订单的单向链接**（`13.13` 的 `orderId`）。
18. ⚠️ **时区不对称**（已实测证实，见 §3.1）：**请求** `planStartAt`/`planEndAt` 用**无偏移**本地 ISO（`2026-09-22T15:00:00`，Java 侧 `LocalDateTime`）；**响应**带 **`+08:00`** 偏移（`spring.jackson.time-zone: Asia/Shanghai`）。
    - ⚠️ **契约 `API:1090` 的请求示例带 `+08:00`，与实现不一致** —— 以本文 §3.1 为准。

## 2. 页面骨架

```
「我的」页
└── 预约列表（独立页）        ← 唯一入口，D5 §6

柜机页（扫码落地）
└── 「预约」次要入口          ← 创建入口，D5 §6
```

- **预约列表挂「我的」页**，与订单列表**分开**（§6）。
- **创建入口只在柜机页**（§6）。
- 预约**没有**详情页 —— **C 端没有预约详情端点**，列表项的 12 个字段就是全部可得信息（§1.11）。做详情页只能把列表字段重排一遍，是纯粹的浪费。

## 3. 创建路径（`13.12`）

### 3.1 时段选择形态：开始档位 + 时长档位

**不让用户回答「结束时刻」这个抽象问题**，而是回答两个他能答的问题：**什么时候开始**、**要占多久**。

| 维度 | 取值 |
|---|---|
| **开始** | 档位网格，**步长 30min**（`:00` / `:30`） |
| **时长** | 档位：**1h / 2h / 4h / 8h** |
| 提交 | `planStartAt` = 所选档位；`planEndAt` = `planStartAt` + 时长 |

**为什么这个组合能让 `8006` 三条规则在 UI 层不可能被触发**（这也是本节最主要的价值）：

| `8006` 规则 | 为什么不可能触发 |
|---|---|
| `end > start` | 时长档位恒 > 0 |
| 时长 ≤ `maxHours`(24h) | 最长档 8h < 24h |
| `planStartAt` 严格晚于 now | 档位**只渲染未来**（§3.2） |

⇒ **`8006` 不会出现在正常路径上**，只作为竞态兜底（§3.2）。

**时区口径（硬约束）**：请求体用**无偏移本地时间**：

```
{ "lockerId": 11, "cellType": "MEDIUM",
  "planStartAt": "2026-09-22T15:00:00",     ← 无偏移，不是 +08:00
  "planEndAt":   "2026-09-22T17:00:00" }
```

⚠️ **不要**照抄契约 `API:1090` 的示例（它带 `+08:00`，与实现不符，§1.18）。解析响应时相反：响应值是**带 `+08:00`** 的字符串。

### 3.2 档位与「当前时刻」

- **只渲染未来的档位**，并在当前时刻之后**留一个安全余量**（起点至少是当前档位的**下一个**档），避免「用户选了、走到提交时刚好过点」的竞态。
- ⚠️ **这一条与 §5 的「窗口外不禁用」是两回事**，理由必须写清：`planStartAt > now` 用的是**客户端自己的时钟** + **服务端回显的 `planStartAt`**，两者都可得，**客户端算得出来** ⇒ 不违反 `04` §11。而窗口的两个端点依赖 `holdMinutes` / `noShowMinutes`，**C 端算不出来** ⇒ 不能据此禁用。
- 兜底仍靠 `8006` 的 `message`（竞态、时钟偏差）：照 `04` §5.2 的通用规则按 `message` 直出（`8006` 不是 `5004`，**不走特判**）。

### 3.3 创建校验失败的归因

| 码 | 触发 | 表现 |
|---|---|---|
| `5004` | 账号受限 | **直接引用 `04` §5.1** 的统一受限文案（`04` §11 明文要求 D5 引用而非重新裁决） |
| `4004` | 柜机不可用 | **直接引用 `04` §9**（「换一台或稍后再试」） |
| `8002` | 该格口类型无空闲 | **直接引用 `04` §9**（「换一种类型或换一台柜机」） |
| `8006` | 时段非法 | 按 `message` 直出（正常路径不可达，仅竞态兜底） |
| `8007` | 同时段已有 `PENDING` 预约 | 「你在这个时段已经有一个预约了」（半开区间相交，**首尾相接不算冲突**） |

⚠️ **`4004` / `8002` 在创建侧不复述文案**，直接引 `04` §9；**转单侧的 `4004` 另给一份**（§4.2）—— 因为两处的**出路不同**。

### 3.4 余位为 0 时

承 `01` §6.1：**余位 0 时不得引导「去预约」** —— 预约同样只认 `FREE` 格口（`13.12` 无空闲 → `8002`），唯一真出口是「换一台柜机」。**本节不推翻该结论**：`cellAvailability[type] === 0` 时，柜机页的「预约」入口**与「开始存件」同样置灰**并写明「该规格已满」。

## 4. 转单路径（`13.15`）

### 4.1 动作落点：预约列表行内

**`PENDING` 行内给「开始使用」按钮**。

- **按钮始终可点，只有 `status !== PENDING` 才不出现**。
- ⚠️ **不按窗口置灰** —— 窗口起点/终点 C 端算不出（§1.2/§1.3）。用 `planStartAt` 可以做**文案**提示（如「请在预约时段开始后使用」，`planStartAt` 是服务端回显的合法值），**但不据此禁用**。
- 窗口外点击 → `6202`，按 `message` 直出（`6202` 不是 `5004`，**不走特判**），具体措辞归 **T1 #13**。

> ⚠️ **与 `03` §5 的关系（看似矛盾，实则不然）**：`03` §5 定了「订单列表行内不放任何动作按钮」。**那条的理由是「取消需要解释、行内放不下」**（`03` §7），而预约的取消/使用**不需要**额外解释（§4.3）。两条裁决的差别来自**动作是否需要解释**，**不是**「行内能否放按钮」这条形式规则。转单后进详情/等待态是另一回事（§4.2）。

### 4.2 转单成功后的落点

`13.15` 返回 `{orderId, orderNo, cellNo}`，且**同事务已生成 `OPEN_CELL(USER_DROP)` 指令**。

**直接跳进该订单的「等待关门」等待态**（`P1 #12` 的组件）。

- 理由：转单的**唯一目的**就是开门存件，指令已发出，用户此刻正站在柜机前 —— 让他先看到「预约已使用」再自己去找订单，是白白浪费他站在柜门前的这段时间。
- `orderId` 已在响应里，**无需重查**。
- ⚠️ **这里不能说「请在 N 分钟内放入」** —— `openTimeoutMinutes` 只有 `13.7` 回显（§1.2），转单路径拿不到。只说「柜门已开，请放入物品后关门」。
- ⚠️ **必须与 P1 复用同一个等待态组件**，不能各做一套。

**`4004` 在转单侧的表现（单独一份，不复用创建侧）**：

| 码 | 处境 | 出路 |
|---|---|---|
| `4004` | 你约的那台柜机现在不可用 | 「预约的柜机暂时不可用」+ **联系客服**（⚠️ **格口已分配给这个预约，换不了**，所以不能照抄创建侧的「换一台柜机」） |

### 4.3 转单不可逆的用户表达

预约置 `USED` 是**终态**：关联订单即使被取消，**预约也不会回退**。

- **不向用户暗示「可以恢复预约」** —— 后端没有回退路径，任何「恢复」暗示都是假的。
- `USED` 行显示为终局（中性档），**不提供任何动作**。

## 5. 窗口与爽约的表达（核心约束：C 端拿不到数字）

### 5.1 窗口怎么说

**不暴露任何分钟数**（`holdMinutes` / `noShowMinutes` 禁止展示，`04` §11）。

- ✅ 可以说：「预约时段**前后一小段时间内**都可以开始使用」
- ❌ 不能说：「可提前 **15** 分钟」「请在 **10:30** 前使用」

**替代手段 = 状态驱动**：窗口外点击由服务端裁决（`6202`），窗口内自然可成功。**具体的分钟数由后端在 `6202` 时刻说了算**。

### 5.2 爽约预警能做到多强：**只做常驻说明，不做事前横幅**

- 预约确认处与预约列表各写一句常驻说明（`PENDING` 行）。
- ⚠️ **不做「即将到期」横幅**。理由：**无推送通道 ⇒ 用户不打开 App 就看不到任何提醒**，横幅会给一个「我提醒过你了」的假象；而 `holdMinutes=15` / `noShowMinutes=30` 是极短窗口，靠用户主动打开 App 来预警，**命中率太低**。
- **代价照实记**：**不做有效的事前预警，这是一个已知的体验缺口**。承 `04` §3 的纪律 —— 爽约后果只在「我的」页与预约流程内解释，**不挂全局横幅**。

### 5.3 爽约后果：讲机制，不讲数字

- ✅ 可以说：「爽约会**影响信用分**，信用分过低会**导致账号受限**」
- ❌ 不能说：扣几分（10）、阈值多少（60）、多久解除（`releaseCondition` 不在 C 端契约，`04` §1.4）
- 术语用「**信用分**」，**不用「积分」**（承 `04` §2）；「黑名单」不进用户文案。

### 5.4 爽约与故障失效必须分开（归因纪律）

| 状态 | 含义 | 文案方向 |
|---|---|---|
| `NOSHOW` | **用户没去**（扣分） | 「未在预约时段内使用，已记为**爽约**」+ 提示影响信用分 |
| `EXPIRED` | **柜机/格口故障**（不扣分，系统无责） | 「因柜机故障，预约**已自动失效**」+ 明确「**不影响信用分**」 |

理由：承 `04` §2「受限 vs 单笔校验被拒必须一眼分开」的同一条原则 —— **归因必须准确**。`EXPIRED` 用户被含糊对待会以为自己爽约了、去查信用分、甚至找客服；而 `NOSHOW` 用户必须确知这是自己的责任，否则 §5.3 讲的机制没有落点。

> ⚠️ **`CANCELLED` 不区分谁取消的**：`cancelSource`（`USER|ADMIN|SYSTEM`）**不在 C 端契约**（§1.11）⇒ 只能笼统说「已取消」，**不猜是谁取消的**（承 `04` §5.3 归因纪律）。

## 6. 列表模型与入口位置

### 6.1 预约列表 = 独立页，入口在「我的」页

**不与订单同列**（`03` §12 留问的答案）。

理由：

1. `13.13` 与 `13.8` 是**两个端点、两套字段**（预约有 `planStartAt`/`planEndAt`/`resvNo`，订单没有；订单有 `payAmount`/`pickupCode`，预约没有）—— 合并需要客户端造**第三条数据流**，而 `03` §2 已明确反对这类客户端自造语义。
2. 预约是**低频、前置**的动作（为未来锁位），订单是**高频、回访**的（`03` §2 首屏第一动机 =「我东西还在里面」）—— 把低频前置物塞进首屏会稀释它。
3. `13.13` **同样无 `createdAt`**（§1.11），与 `13.8` 同病，合并后排序无解。

**转单后**：预约行置 `USED`，订单列表出现新单 —— **两个列表各自说实话，不做「演进」的视觉叙事**（跨端点的演进叙事需要客户端状态，违反 `03` §4「不引入客户端侧的新数据」）。

### 6.2 单流不分组 + `PENDING` 上浮

**照搬 `03` §2 的单流模型**（同一条理由：单值 `status` + 分页 + 无 `createdAt` 三条叠加，任何分组都在客户端自造与枚举错位的筛选语义），**外加**：

- **`PENDING` 上浮**，规则与 `03` §3 **逐字一致**：只发生在**第一页内**、组内保持服务端顺序、**跨页不置顶**、**不加分隔标题**。
- 理由：预约列表的第一动机与订单列表**不同** —— 订单是「我东西还在里面」，预约是「**我的待使用预约什么时候到**」。`PENDING` 是唯一需要用户行动的（去使用或去取消），终局行只是留痕。
- ❌ **默认只请求 `status=PENDING` 被否决**：会让用户看不到「我约过但爽约了」的留痕，而爽约正是他需要知道的（§5.3 讲了机制，这里要把结果给他看）。

### 6.3 分页与刷新

| 事项 | 口径 |
|---|---|
| 首屏 | `pageSize = 20`，`status` **不传**（全部） |
| 加载更多 | 上拉触底；**终止条件只能是「已加载条数 ≥ `total`」**（越界钳制到末页，靠空数组判断会无限重复末页） |
| `onShow` | **静默刷新并重置回第一页** |
| 下拉刷新 | 同上 |
| 常驻轮询 | **不做** |

- **重置而非增量刷新**：承 `01` §3.2「不做本地业务数据缓存」。预约状态会在翻页之间变（爽约由定时任务置位，§1.16），保留陈旧后续页等于让列表撒谎。
- **不轮询**：爽约是异步置位的，**轮询到它也不会改变用户当下能做什么**（窗口已过，无可挽回）。

## 7. 显示态（5 个枚举 → 5 个显示态）

| 枚举 | 显示态 | 性质 | 语义档 | 动作 |
|---|---|---|---|---|
| `PENDING` | **待使用** | 在途 | 正常（品牌绿） | 「开始使用」+「取消预约」 |
| `USED` | **已使用** | 终局 | 中性（灰） | 无 |
| `CANCELLED` | **已取消** | 终局 | 中性（灰） | 无 |
| `NOSHOW` | **已爽约** | 终局 | **危险（红）** | 无 |
| `EXPIRED` | **已失效** | 终局 | 中性（灰） | 无 |

- **枚举与显示态一一对应，无合并**（与 `03` §4 的 11→9 不同，预约的五个枚举在用户视角本就是五件事）。
- **`NOSHOW` 走危险档**：它是唯一**已发生扣分**的状态，必须一眼可辨（与 `03` §6「已超时」走危险档同理由 —— 需要用户立刻理解的负面后果）。
- 语义色只做**色条 / 标签背景与边框**，**标签文字一律走 ink**（承 device spec V25，与 `03` §6 同）。
- **具体 token 由 T2 #14 出**。

## 8. 取消路径（`13.14`）

- **`PENDING` 行内给「取消预约」**，与「开始使用」并列。
- ⚠️ **始终可见、点击后解释**（§4.1 同原则）：`PENDING` 虽是本地可见字段，但预约会因柜机故障转 `EXPIRED`、因到期转 `NOSHOW`，**这些转变发生在用户没打开 App 的时候** —— 本地快照会造出「本地说能取消、服务端说不能」的**双源真相**（承 `04` §5 第 1 条）。
- 非 `PENDING` 点击 → `6202`，按 `message` 直出。
- **取消不扣分**（§1.14），界面上**不需要**任何警告话术 —— 这是与爽约（§5.3）的关键区别。
- **无任何时间限制**（§1.14）：窗口已开、甚至过了 `planStartAt` 仍可取消。**不据此做任何禁用或倒计时**，因为那两个时刻 C 端算不出。

## 9. 与「受限」（`5004`）的关系

**直接引用 `04`，不重述**（`04` §11 明文：「D5 #9 直接引用本条，不重新裁决」）。

| 动作 | 受限时 |
|---|---|
| 创建预约（`13.12`，入口在柜机页 §6） | **保持可见可点** → `5004` → `04` §5.1 的统一受限文案 |
| 开始使用（`13.15`，列表行内 §4.1） | **保持可见可点** → `5004` → 同一份文案 |

- **不置灰、不隐藏**（承 `04` §5.1）。
- ⚠️ **取消预约（`13.14`）不被 `5004` 拦** —— 它是**收尾动作**，受限用户手上的预约照样能取消（承 `04` §1.2「能看、能做完手上的、不能开新的」）。**列表页不给 `PENDING` 行加任何受限标记。**

## 10. 刻意不做（避免被当成漏做）

- **不做预约详情页** —— C 端没有该端点（§1.1），列表字段就是全部。
- **不做时段查询 / 可选时段端点** —— 后端没有，档位由 C 端定义（§3.1）。
- **不做精确时间 picker**（用户答不上「结束时刻」）。
- **不展示任何分钟数 / 扣分 / 阈值 / 剩余天数**（§5.1/§5.3，承 `04` §11）。
- **不做事前爽约预警横幅**（§5.2）。
- **不按窗口置灰「开始使用」**（§4.1）。
- **不按状态置灰「取消预约」**（§8，避免双源真相）。
- **不做预约与订单的合并列表 / 演进叙事**（§6.1）。
- **不做预约列表轮询、不做本地预约数据缓存**（§6.3）。
- **不做「恢复预约」入口** —— `USED` 不可逆（§4.3）。
- **不区分「谁取消的」** —— `cancelSource` 不在 C 端契约（§5.4）。
- **不展示 `resvNo` / `orderId`**（§7.1）。

## 11. 登记项（跨仓库备忘，**不改任何代码**）

1. **契约文档的时区示例与实现不符**：`API:1090` 的 `13.12` 请求示例带 `+08:00`，而实现是 `LocalDateTime`（无偏移）。C 端按 §3.1 执行。**本 effort 不提议改文档**（属后端文档仓）。
2. **预约链路缺参数回显**：`13.7` 回显 `openTimeoutMinutes`，而预约侧**没有任何对应回显**（`holdMinutes` / `noShowMinutes` 均不可得）⇒ C 端做不了窗口倒计时、做不了有效爽约预警（§5.2 的代价）。与 `04` §12 第 2 条同类，都是**保守方向**（宁可不报，不许说错）。
3. **C 端无预约详情端点**，且列表缺 `createdAt` / `cancelSource` / `expireReason`（管理端 8.2 都有）⇒ C 端说不出取消原因、区分不了「用户取消」与「系统取消」（§5.4）。本 effort **不提议改后端**。
4. **`13.8` / `13.9` 不返回 `reservationId`** ⇒ **订单 → 预约方向在 C 端完全没有链接**，只有单向（预约 → 订单）。本 effort **不提议改后端**。
5. **`SysParamInitializer` 初始化 20 个冻结 key**（18 + 增量 #13 的 `auth.*` 2 项），与 `API:872` 表述一致 —— **不是缺口**，记此以免后人误判为文档漂移。
