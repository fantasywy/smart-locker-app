# 小程序 C 端维持原生 TS + Sass，不引跨端框架

小程序 C 端（`/api/app/v1/**`）**只有微信一个目标端**，未来也没有第二个已命名的端。我们决定：**维持原生 TypeScript + Sass**（官方 quickstart 骨架，`project.config.json` 已开 `useCompilerPlugins: ["typescript","sass"]`、`miniprogramRoot: miniprogram/`），**不引入 Taro / uni-app**。

**Considered options**：

- **引入 Taro（React）** —— 否决。Taro 的全部价值在于「一套代码编到多端」，而本 effort 的 destination 里**没有第二个端**：目标端只有微信小程序。为未命名、未排期的跨端可能性，现在付出的是编译层抽象、`wx.*` 能力的编译期不确定性、以及**整个样式变量层的重做**（见下方 Consequences）。这正是「提前优化」的教科书形态。
- **引入 uni-app（Vue）** —— 否决。除上述跨端成本外，还多一层「与兄弟仓库语法一致」的诱惑：`smart-locker-admin` 与 `smart-locker-device` 都是 Vue 3 + Vite，但它们跑在 **Web 运行时**，小程序是**完全不同的运行时**（无 DOM、无 CSS 变量、无 npm 直装）。语法一致不会带来任何代码复用，只会让「这块能不能照抄 device」这个判断持续产生误导。ADR-0001 已经踩过一次同类陷阱（屏端能力不可移植）。
- **自建轻量 request 库/中间件栈** —— 否决。这是「自己养一套基础设施」，收益是隔离性，代价是长期维护面。一期 16 个端点不需要它；§请求层形态 用 Promise 封装已足够。

**Consequences**：

- **T2（#14）的变量层不需要重做** —— 票面已写明「若 D7 选择跨端框架，T2 的变量层实现需要重做」；本裁决消除了这个已知代价。T2 按原生 SCSS 变量 + mixin 出草案即可，且**该草案从此是终稿的基础**，不再是一次性材料。
- **小程序无 CSS 变量这一事实成为长期约束** —— 色调层只能落成 SCSS 变量（编译期）+ mixin（生成具体规则）。device 那套 `var(--x)` 做法**不可照搬**。这是本裁决的直接后果，T2 承担。
- **微信特有能力零损耗可用** —— `wx.login` / `wx.scanCode` / `open-type="contact"` / `open-type="chooseAvatar"` 全部直接可用，没有编译层转译风险。这几项都是 `01`–`06` 的承重能力（隐式前置登录、扫码入口、客服唯一出口、昵称头像填写）。
- **接受「将来若要跨端，是一次重写」** —— 与 ADR-0001 同构的取舍：把跨端成本从「现在支付、将来受益」改成「将来真需要时再支付」。若真要跨端，届时是一次有明确收益的迁移，而不是现在的一次投机。
- **放弃与兄弟仓库的语法统一** —— 三个端将长期是「Web 用 Vue、小程序用原生 TS」，这是运行时差异的真实反映，不是疏漏。
