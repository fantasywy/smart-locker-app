# 附近柜机：C 端可只读浏览，写动作仍只能来自扫码

C 端产品方向已确定「附近柜机」作为独立 tab 进入小程序（完整地图页：搜索 + 地图 + 底部站点卡 + 定位 + 列表降级），而后端 C 端（`/api/app/v1/**`）**没有**任何站点 / 附近端点。ADR-0001 当时裁决「C 端一期不提供任何形式的柜机浏览能力」，理由是两条前提：「一期是单站点形态」，以及「用户要用柜机时必然站在柜机前」。第一条前提已被产品方向推翻；第二条只在**写动作**上成立 —— 用户提前知道附近哪里有柜机、还有没有格口，并不需要哪扇门被打开。

我们决定：**C 端允许只读的附近柜机浏览，但浏览不产生 `lockerId`。** 具体是：

- **按站点聚合**：一个站点一张卡（名称 / 地址 / 距离 / 营业时间 / 四档余位合计 / 站点可用状态）；柜机在卡内只作为明细（位置 + 状态）。站点是**唯一**带经纬度的实体，柜机自己没有坐标。
- **只读**：附近页不出站到柜机页，不提供存件、预约等任何写动作；需要 `lockerId` 的动作（`13.7` 存件、`13.12` 预约）仍然只能由扫描柜机码 → `13.6` 得到上下文。
- **定位是增强，不是前置**：定位失败时城市 + 搜索仍可用，只是没有距离、也不按距离排序；半径默认 3 km、可一键扩到 10 km，搜索在所选城市内、不受半径限制。
- **排序两段式**：可存件 → 已满 → 暂不可用；组内按距离升序，距离相同按站点名升序；服务端排序，客户端不重排。
- **停用不挡营业**：`site.status = DISABLED` 只表达后台处置，既不在附近结果里隐藏，也不能当作营业状态；可用性只看柜机。
- ADR-0001 的其余部分**继续有效**：柜机上下文只作页面参数、不写 `storage`、不缓存「上次的柜机」。

**Considered options**：

- **维持 ADR-0001 原样，不做附近柜机** —— 否决。产品方向已确认独立 tab + 完整地图页；维持禁令等于让 C 端只能在「人已经站在柜机前」时才知道柜机存在，用户无法在家判断「要不要出门、去哪一个站点」。
- **允许附近页直接下单（远程建单）** —— 否决。开门会发生在用户不在的那台柜机上，这正是 ADR-0001 里最重的那条风险（「下单成功而门在别处打开」）；省下的只是一次扫码。
- **允许附近 → 柜机页的只读形态，并支持远程预约** —— 本期否决。它要把柜机页拆出「只读模式」（该页全部不变量都建立在「上下文来自扫码」上），并把远程写动作（锁住格口）引入附近，契约与状态都要重做。留作二期评估，本 ADR 不预设它一定会做。
- **按柜机聚合而不是按站点** —— 否决。`Locker` 实体没有经纬度，同站点内所有柜机距离完全相同，列表会被「同一地址 × N」灌水；站点才是用户真正要去的那个地方。
- **先用本地假数据 / 缓存上次附近结果把入口放出来** —— 否决。与 ADR-0001 同一条纪律：不做假入口；端点未上线前「附近柜机」tab 不露出。

**Consequences**：

- **跨仓库改动**：后端需要新增 C 端只读端点（站点 + 柜机明细 + 四档余位，含 geo 查询与索引）。契约由设计 spec 定义并标注「后端待建」；后端实现与排期不属于本 effort。
- **扫码链路零改动**：柜机页、`13.6`、`13.7`、`13.12` 的行为都不因本裁决改变；附近 tab 只是一个新增的只读入口。
- **预约仍必须扫码**：这是 ADR-0001 保留部分的直接后果，也是附近柜机暂时不能「提前占格」的体验缺口 —— 已知、可接受，二期再议。
- **小程序侧新增能力与风险**：`wx.getLocation`（`requiredPrivateInfos`、隐私协议、类目审批）、`map` 组件（iOS 同层渲染可能失败，需 `bindrendererror` + 列表降级）、`wx.openLocation` 导航。定位授权被拒或类目未批时，城市 + 搜索这条路径必须独立可用。
- **站点数据质量成为承重面**：`site.city` 是自由文本、`site.lng` / `site.lat` 允许为空；城市兜底与距离排序都依赖这两项，缺坐标站点如何处置需在契约层定死。
- **ADR-0001 部分失效**：其「不提供任何形式的柜机浏览能力」与「柜机上下文只能由扫码得到」中的**浏览**部分被本 ADR 取代；「`lockerId` 只能来自扫码、上下文只作页面参数、不写 storage」继续有效。
