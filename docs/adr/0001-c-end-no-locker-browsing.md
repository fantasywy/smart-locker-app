# C 端不做柜机浏览，柜机上下文只能来自扫码

小程序 C 端（`/api/app/v1/**`）里，唯一能确定「用户要用哪一台柜机」的入口是扫描柜机二维码 → `13.6 GET /lockers/by-code?code=<柜机码>`。后端**没有**站点列表 / 附近柜机端点，用户在 App 内无法浏览或搜索柜机。而需要 `lockerId` 的动作只有两个 —— 创建存件订单（`13.7`）与创建预约（`13.12`），两者都发生在用户**站在柜机前**的时刻。

我们决定：**C 端一期不提供任何形式的柜机浏览能力**（不新增端点、不做本地假数据、不缓存「上次的柜机」）；「柜机上下文」只能由扫码得到，且只作为**页面参数**存在，不写入 `storage`、不跨页共享。

**Considered options**：

- **增设站点列表 / 附近柜机端点** —— 否决。一期是单站点形态，且会连带引入定位授权、站点排序、离线柜机如何展示等一串新口径，收益远小于成本；更重要的是它会把「必须站在柜机前」这个真实约束从产品里抹掉。
- **让中控屏显示小程序码、用户在小程序内扫屏上的码** —— 否决。屏端现行实现下「扫码 tab」扫的是**柜机码**，且屏端**没有入站扫码能力**（见 R2 findings）；屏侧改造属 Out of scope。
- **把柜机上下文持久化到 `storage`、冷启动恢复「上次的柜机」** —— 否决。最坏结果是用户在另一台柜机前被带上别的柜机的上下文，下单成功而**门在别处打开**；省一次扫码的收益与开错柜门的风险严重不对称。

**Consequences**：

- 柜机二维码的**载荷格式成为跨端契约**：柜机贴纸 / 平台二维码规则 / 小程序解析三者必须一致，已定为 `https://<域名>/l/{lockerCode}`。
- 扫码成为最前置的入口，其体验依赖平台「扫普通链接二维码打开小程序」的四条前置（企业主体、ICP 备案域名、校验文件、已发布线上版本）。缺任一条即退化为「必须先打开小程序、再扫柜机码」。
- **预约同样要扫码才能创建**（预约也需要 `lockerId`）；预约创建后的到点使用（`13.15`）按 `reservationId`，不再需要柜机上下文。
- 若将来要支持「浏览附近柜机」，这是一次**跨仓库**改动：必须同时改后端（新端点）、本 ADR、以及 C 端信息架构（首页将多出一个柜机列表入口）。
