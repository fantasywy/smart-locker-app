### 关键事实（票面隐含假设不成立，须先纠正）

D2 票面把「小程序出二维码给屏扫 vs 屏上敲 6 位码」当成 A/B，隐含「屏上敲码 → 开门」。**代码里不成立**：

- 开门只能由服务端下发的 `OPEN_CELL` 指令驱动，指令来源**只有三个**：
  1. `13.7 POST /orders` 下单 → `USER_DROP`
  2. `13.11 POST /orders/:id/pay` 支付 → `USER_PICKUP`（**支付即开门**）
  3. 管理端手动开箱 → `ADMIN_FORCE`
- **屏端 `pickup-verify` 不产生任何指令** —— 只回摘要 + `paid` + `hint`（`PickupVerifyServiceImpl.java:50-71`）。
  屏端后端原文 hint：`paid:false` →「请在小程序完成支付后取件」；`paid:true` →「请在小程序点击取件开门」。
- ⇒ **取件码没有开门力**；真正开门发生在**小程序的 13.11**（幂等：已付清再调不重复扣费、只重发指令，`openCommandIssued` 告知本次是否下发）。
  - `AppPickupPaymentFlowTest`：`pay_freezesFees_recordsIncomeAndIssuesPickupCommand`、`pay_repeated_doesNotDoubleCharge_butReissuesPickupCommand`、`pay_notYetStored_returns3002`、`pay_afterPickup_returns3002`。
  - `需求分析文档.md:157` 亦写明「小程序入口：进行中订单 →『取件』→ …→ 生成开门指令（`USER_PICKUP`）」。
- 屏侧唯一取件入口是键盘键入 6 位码；屏端**无入站扫码能力**（R2 已证）⇒「出码给屏扫」需屏侧改造，Out of scope。

### `13.11` 的取值细节（第二轮用到的硬事实）

- 允许时机 = 已存入未取件（`IN_PROGRESS|TIMEOUT` ∧ `startAt≠null` ∧ `endAt==null`）；**未存入 → `3002`**（存件期的开门由 `13.7` 下单自动下发的 `USER_DROP` 承担）；已取件/终局 → `3002`。
- `TIMEOUT` 单：支付时刻现算**差额**（累计应收 − 已付），已付清不扣费。
- 幂等：已支付未取件 → 不重复扣费 + **重发 `OPEN_CELL(USER_PICKUP)`** + 返回首次支付信息。
- ⚠️ **`paid` 与 `openCommandIssued` 一期都是写死的 `true`**（`AppOrderServiceImpl.java:199`）⇒ `openCommandIssued` 不是「指令下发了」的证据，C 端**不许**据此渲染「门已开」；唯一证据是 `DOOR_CLOSED` 驱动的状态推进。这条是交给 P1 的输入。

### D3 的事实底稿（自己查的，未派 subagent）

- **列表契约 §13.8**：`GET /api/app/v1/orders?status=&page=&pageSize=`。`status` 是**单值**枚举（`PENDING_PAYMENT|IN_PROGRESS|COMPLETED|TIMEOUT|FORCE_ENDED|REFUNDED|CANCELLED`），**没有多值 / 分组参数**。
- **列表项字段**（`AppOrderListItemVO.java`）：`id / orderNo / lockerId / lockerNo / siteName / cellNo / cellType / startAt / endAt / status / payAmount / estimatedAmount / pickupCode`。**没有 `createdAt`**，**没有 `openTimeoutMinutes`**。
- **服务端排序**（`AppOrderServiceImpl.list()`）：`.orderByDesc(Order::getId)` —— 即下单倒序，客户端不排序即可。
- **`openTimeoutMinutes` 只出现在 13.7 建单响应**（`CreateOrderVO`），列表与详情都没有 ⇒ 冷启动后无法知道未存入单的时限基准。
- **真实截止时刻是两段式**（`NotYetStoredDeadline.stageOf`）：第一程 = `createdAt + openTimeoutMinutes`；**开门指令未回执 `DONE`** → 取消；**已回执** → 延长一程再看，超期标记「开门未闭」。指令是否 `DONE`（`openAcked`）**C 端完全看不到** ⇒ 任何客户端倒计时都可能说谎。
- 「开门未闭」判定 `awaitingReview` = `openedNotClosedAt != null && status == IN_PROGRESS`，而 `openedNotClosed` **不在 C 端 §13.8/§13.9 契约内**（R3 唯一真缺口）⇒ C 端只能漏报，`IN_PROGRESS + startAt=null` 长期不动与「已延长一程」不可区分。
- **TIMEOUT 跨两类**：`endAt == null` 是在途（待补缴/待取件），`endAt != null` 是已终局 ⇒ **按 status 分组会把同一枚枚举劈成两半**，「进行中 / 已完成」两级模型与枚举错位。
- 状态机（需求 §4.5）：`IN_PROGRESS`（含未存入 `startAt=null` 与使用中）→ `CANCELLED` / `COMPLETED` / `TIMEOUT` / `FORCE_ENDED` / `REFUNDED`；`PENDING_PAYMENT` 一期不启用。
- 屏端色调层事实源：`vue/smart-locker-device/.scratch/device-simulator/spec.md` V9/V25（语义色只做背景/边框/圆点/色条，文字走 ink；琥珀 ink `#976a27`、红 ink `#c05454`、绿用 `$color-primary-active #008655`）。
- 分页：`PageSupport.DEFAULT_PAGE_SIZE = 20`、上限 100、**越界钳制到末页** ⇒ 上拉加载的终止条件只能是「已加载条数 ≥ total」。
- 行内版式的空间维度：device 侧门面只有**物理门号 `01`–`15`**（device spec V3），C 端只有 `cellNo`（`M05`），映射表不在 C 端契约 ⇒ 登记项，不改两边。
