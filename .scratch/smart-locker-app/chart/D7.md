**Type**：`wayfinder:grilling`（HITL）
**Blocked by**：无 —— 在 frontier 上

## 要裁决什么

1. **技术栈**：沿用原生 TS + Sass 骨架，还是引入 Taro / uni-app？决策依据要写出来（不是偏好）。要考虑：C 端**是否需要跨端**（若只要微信，原生更省）；`wx.requestPayment` 一类微信特有能力的可用性；团队对两边的熟悉度；以及**小程序无 CSS 变量**这一事实对样式层的影响（见 T2）。
2. **请求层形态**：token 刷新与 `401 + 2005` 的**静默重试一次**怎么封装（拦截器 / 中间件）、并发 401 如何避免刷新风暴（单一飞行 + 排队重放）、`code` 无效 `8001` 的首登自动注册怎么并入登录流程。
3. **是否分包**：页面清单规模（订单 + 预约 + 支付 + 取件 + 个人/信用分）是否触发分包；主包首屏要装什么。
4. **状态管理**：全局需要哪些跨页状态（登录态、进行中订单、柜机上下文）—— 用原生 `app.globalData` + 事件，还是引一个轻量 store。
5. **类型来源**：后端 v1.0 契约在前端如何落成类型（手写 / 脚本生成）—— 注意 `smart-locker-admin/docs/adr/0002`：**前端不得自造契约**，所以这里要定「怎么引用」而不是「怎么设计」。
6. **工程约束**：包管理 pnpm、`useCompilerPlugins: ["typescript","sass"]`、`miniprogramRoot: miniprogram/` 是否维持。
