**Type**：`wayfinder:prototype`（HITL）
**Blocked by**：无 —— 在 frontier 上，且是 C 端**最独特**的交互

## 要回答什么

**「支付成功 ≠ 拿到东西」。** 两个机制叠加，让 C 端出现一个别处没有的等待态：

- **只有 `DOOR_CLOSED` 驱动订单状态与计时起点**；`OPEN_CELL` **不改**订单状态。→ 用户必须被明确告知「我们在等你关门」，否则会停在一个不推进的界面上反复点。
- 指令生命周期 `PENDING → SENT → DONE/FAILED`，`SENT` 超 5min → `EXPIRED`，且**失败/过期不自动重发**，只能由用户动作重新生成新指令。→ 必须有一个**自然的**重试入口，而不是让用户面对一个静默死掉的界面。

用原型回答这两个问题：

1. **这个等待怎么让人不焦虑**：进度怎么表达（不可撒谎 —— 没有可靠的服务端进度，只有状态轮询）？要不要语音/视觉上的「柜门已开」强反馈？等待期间给什么可做的事（例如先展示取件码位置、先讲下一步）？
2. **失败怎么自然地重试**：`FAILED` / `EXPIRED` / 「开门了但没关」三类中断各对应什么界面与什么措辞？重试是原地重发还是先解释再重发？重试失败第二次还怎么走？

## 这是原型，不是规格

产出**回答问题的证据**，不是最终设计：

- 一个能跑起来的交互原型（一次性，可弃），覆盖至少四条路径：正常关闭 → 推进；超时未关；指令 `FAILED`；指令 `EXPIRED`。
- 一份 README，写明：**哪些纸面推不出来的问题被回答了**、哪些仍然存疑、原型里为了跑通而做的假假设。
- 原型代码定位为 throwaway —— 目的是逼出结论，不是留作实现基础。

## 约束

- 状态与文案要与中控屏九态语义对齐（屏上「待机 / 输入中 / 校验中 / 已付清 / 待支付 / 无效 / 已核销 / 传输失败 / 业务拒绝」）—— 尤其**传输失败**与**业务拒绝**对应 C 端什么。
- **不得假装有推送**：无推送通道，状态更新只能靠拉取；原型的「实时感」只能建立在轮询上，且轮询策略本身要作为结论之一写出。
- 不裁决支付形态（D6）、不裁决取件码流转（D2）；本 ticket 只吃它们给出的前置状态。
- 不改后端、不改柜机（Out of scope）—— 需要设备端行为时**用 stub 模拟**。
