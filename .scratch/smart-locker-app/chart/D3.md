**Type**：`wayfinder:grilling`（HITL）
**Blocked by**：R3（三个未闭合口径的确切表述）

## 要裁决什么

订单首页如何在**有限首屏**里表达这些状态：**未存入 / 使用中 / 已完成 / TIMEOUT / 开门未闭**。

1. **分组还是筛选**：这些状态是并列 tab、还是「进行中 / 已完成」两级 + 进行中内部再分？
   - 依据 R3 findings（分支 `research/r3-open-gaps`）：后端**明示不拆分**（`需求分析文档.md:451`、`API设计文档.md:1357` ②），列表 API 只提供 `status` 枚举、**无独立筛选项**，**拆分权在 C 端**。所以这不是「数据层分不开」，而是「数据层给了信号、拆不拆由你定」。
   - 唯一数据信号是 `startAt === null`：`未存入 = status==='IN_PROGRESS' && !startAt`。后端对未存入的 `estimatedAmount` 返回 `null`，计时/费用本就没有值可显示。
   - **代价已变**：可以放心拆，但要自己承担派生逻辑与空值渲染。
2. **首屏第一眼看到什么**：用户打开小程序最常做的是「我东西还在里面，取件码给我」还是「我有个单没弄完」？这决定排序与置顶策略。
3. **异常态怎么浮现**：`TIMEOUT`、**开门未闭**、`CANCELLED`、业务拒绝 —— 是混在列表里，还是单独一条「需要你处理」带？
   - ⚠️ 依据 R3 findings：「**开门未闭**」在 **C 端契约里没有字段** —— `openedNotClosed` 只挂在管理端详情 §7.2，C 端 §13.9 / §13.8 均不含。要么留白（保守方向：漏报而非误报），要么把「把该字段加进 §13.9」显式登记为联调挂账项 —— **本 effort 不提议改后端**。
4. **「未存入」的紧迫感**：未存入的订单还在计开门超时（`openTimeoutMinutes`），要不要在行内做倒计时/紧迫提示？N2（`Order.startAt` 未存入时是否为空）决定能不能算出剩余时间。
5. **空态与首次进入**：没有任何订单时显示什么。

## 约束

- N2/N4 的裁定结果来自 R3；**不要**假设后端会补齐字段（后端改动在 Out of scope）。
- 语义色/文字口径要与中控屏九态对齐（见 device spec §12 与 D2 的对齐表）。
- 无推送通道：状态更新**只能靠拉取**，所以「进行中」的刷新策略是本 ticket 的一部分。
