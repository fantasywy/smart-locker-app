## D2 裁决：小程序 × 中控屏职责边界 —— 取件码怎么流转

三轮 grilling 收口，**frontier 为空**。正文落 **`docs/spec/02-c-end-device-boundary.md`**（13 节）；术语落新建的 **`CONTEXT.md`**。commit `fcc7908`。

### 决定性事实：票面的前提被推翻

票面把问题设成「小程序出二维码给屏扫 **vs** 屏上敲 6 位码」，隐含假设是「屏上敲码 → 开门」。**不成立**：

- **开门只能由服务端下发的 `OPEN_CELL` 指令驱动**（device `docs/adr/0003`）。指令来源**只有三个**：`13.7` 下单（`USER_DROP`）、`13.11` 支付（`USER_PICKUP`，**支付即开门**）、管理端手动（`ADMIN_FORCE`）。
- **屏端 `pickup-verify` 不产生任何指令** —— 只回摘要 + `paid` + `hint`（`PickupVerifyServiceImpl.java:50-71`）。屏上那两句引导语是**后端写死的原文**：`paid:true` →「请在小程序点击取件开门」；`paid:false` →「请在小程序完成支付后取件」。
- ⇒ **屏上的取件码校验从不开门**；**取件码没有开门力**，它是「带到屏上敲」的**查询凭据**。真开门发生在小程序的 `13.11`。

证据：`PickupVerifyServiceImpl.java:35-36,50-71`、`AppOrderServiceImpl.java:171-200`、`AppPickupPaymentFlowTest`（`pay_freezesFees_recordsIncomeAndIssuesPickupCommand` / `pay_repeated_doesNotDoubleCharge_butReissuesPickupCommand` / `pay_notYetStored_returns3002` / `pay_afterPickup_returns3002`）、`需求分析文档.md:157`。R2 已证屏端**无入站扫码能力**，「出码给屏扫」需要屏侧改造（Out of scope）。

### 裁决（11 条）

1. **分工**：屏 = **只读查询台**（查状态 + 应付参考 + 引导语）；小程序 = **唯一开门发起方**。
2. **取件码的定位**：**查询凭据，不是取件凭据**。唯一用途是在屏上敲入以查出「哪一单、欠多少、付没付」。任何界面不得暗示「凭码取件」。
3. **展示口径**：码**只在订单详情页的固定取件区块**、**常驻可见**（不做「点击才显示」、不做自动隐藏倒计时、不做防截屏）。列表行内不铺 6 位数字，只给进入详情的入口（列表结构归 D3）。
4. **看不到码时**：**只解释「未存入期码尚未生成」**（固定区块占位 + 一句说明，不许留空白）；终局后**不解释、不出现取件区块**。
5. **「取件开门」动作**：一个按钮按状态变形 —— 未清账「支付并开门」/ 已清账「取件开门」/ `TIMEOUT` 欠费「补缴并开门」；**实现 = 幂等调用 `13.11`**；**重试入口就是同一个按钮**（后端注释原话：此前那条指令可能已 `FAILED`/`EXPIRED`，用户重试动作必须重新生成）。**按钮不承载金额** —— `estimatedAmount` / `payable` 只是 5 分钟粒度参考快照，契约明写禁渲染为锁定价。
6. **两个派生判定**：
   - 能不能取件 = **`pickupCode !== null`**（它的返回口径与 `13.11` 准入、`14.6` 校验**同源**，「有码」与「能取件」永远不会打架）；
   - 付没付清 = **`payAmount !== null`**（⚠️ 不是 `> 0` —— **全免单也会落一张 0 元 `SUCCESS` 支付单**，用 `> 0` 会把全免单用户永远卡在「待支付」）。
7. **点完说什么**：只能说「已发出开门指令，请到柜机前取物，取出后关好柜门」+ 等待态。**不许渲染「门已开」** —— 一期 `paid` 与 `openCommandIssued` **都写死 `true`**（`AppOrderServiceImpl.java:199`），证明不了任何事；唯一证据是 `DOOR_CLOSED` 驱动的状态推进（订单转 `COMPLETED`、格口释放、码失效）。
8. **九态对齐**：对齐是**语义级**的 —— C 端**看不到**屏的显示态。屏的待机 / 输入中 / 校验中 / 无效 / 传输失败 / 业务拒绝都是**屏侧局部态**，C 端既不知道也不该假装知道；只有「**已付清**」「**待支付**」对应 C 端取件入口的两个分支，「**已核销**」对应订单已终局。
9. **预期落差**：为消解「输码即开门」的老经验（普通快递柜的心智），详情页取件区块**预先讲清流程**；屏上 `hint` 只作**事后兜底**（它的发现时机是人已经站在柜机前，那是最糟的纠正时机）。
10. **代取判死**：码无开门力 + 开门只认**本人** token（越权 `8003`）⇒「把码发给别人代取」在当前架构下**不可能**。写进「刻意不做」。
11. **取件不可达的兜底**：整套取件绑在「本人微信 + 有网」上，手机没电 / 没网就取不出。详情页取件区块与「我的」页都写明**联系客服**；人工出口是管理端手动开箱 `ADMIN_FORCE`（**不触发自动结算**，后续由 `FORCE_END`/`REFUND` 闭合）。「联系客服」在这里第一次从摆设变成**功能性**出口。

### 边界（本票未裁）

一期渠道形态（纯模拟按钮 vs `wx.requestPayment` 壳）与支付异常分支矩阵 → **D6** `#10`；点完到 `DOOR_CLOSED` 之间的等待态、指令失败 / 过期的界面与措辞、轮询策略、防连点 → **P1** `#12`；列表行内结构、排序、「进行中」置顶、刷新策略 → **D3** `#7`；各分支最终中文文案 → **T1** `#13`；码的呈现与按钮禁用/进行中态 → **T2** `#14` + `#13`。

### 移交说明（跨仓库，**不改任何代码**）

结论：**屏侧不需要改。** 屏上那两句引导语已与本裁决一致，屏端没有任何阻塞取件路径的缺陷。两条**登记项**：

1. **术语同步项**：屏上 `hint` 是后端写死的字符串（`PickupVerifyServiceImpl.java:36`）。C 端按钮名统一为「**取件开门**」；若将来任一方改名，屏上文案**不会跟着变**，需人工同步。
2. **观感冲突（不改，仅登记）**：屏端键盘的提交按钮文案是「**开门**」（`TerminalKeypadTab.vue:111`），但按下只做校验、不开门。与「屏不开门」的事实叠加，会让用户预期「按了就该开」。按 Out of scope **不改屏**；若将来要动，是屏侧的独立议题。

### 一个 ADR 候选（本次**未**写）

「不做代取」满足 ADR 的三条门槛（难回退 / 无上下文会困惑 / 真取舍），但它同时是**没有任何后端端点支持**的顺推事实，不是我们主动选定的方案 —— 按 domain-modeling 的「sparingly」记在 spec §12，不落 ADR。若后续认为「为什么不能像普通快递柜那样把码发给朋友」这个问题需要一份正式 ADR 来回答，再补 `docs/adr/0002-*`（`0001` 已被 D1 占用）。
